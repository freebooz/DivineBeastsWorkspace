# 业务后端本地部署说明

版本：1.0.0
适用范围：`DivineBeastsWorkspace/Backend` 五个 Go 业务服务的 Docker 本地开发部署。
部署性质：开发联调环境；不是生产发布、不是 Kubernetes/Agones 集群部署，也不使用真实支付、数据库或凭据。

## 1. 目标与边界

本说明提供一个可重复执行的本地部署入口：构建并启动 GatewayService、IdentityService、PlayerDataService、MatchService 和 GameServerControlService，逐一确认其 HTTP 就绪端点及 Gateway Swagger 文档入口可访问。

该部署使用 `Backend/internal/app/composition/composition_local.go` 的本地装配：身份、玩家资料、组队、匹配、服务器注册和 Outbox 均使用明确标注的内存实现。它用于验证服务进程、HTTP 路由和跨服务调用，不替代生产持久化、消息发布或游戏服务器编排。

## 2. 服务拓扑与端口

| 服务 | 容器内服务名 | 主机 HTTP 端口 | 主要职责 | 本地依赖 |
| --- | --- | --- | --- | --- |
| GatewayService | `gatewayservice` | `28080`（容器内为 `8080`） | 统一 HTTP 接入、转发身份/资料/比赛请求，并在本地提供 Swagger。 | Identity、PlayerData、Match、只读 `Shared/Contracts` 挂载 |
| IdentityService | `identityservice` | `8081` | 本地身份与会话能力。 | 无外部依赖 |
| PlayerDataService | `playerdataservice` | `8082` | 玩家资料读取与保存。 | 无外部依赖 |
| MatchService | `matchservice` | `8083` | 组队、匹配和比赛请求。 | 无外部依赖 |
| GameServerControlService | `gameservercontrolservice` | `8084` | 本地世界/竞技分配、转移票据和 Outbox Worker。 | 无外部依赖 |

所有容器均处于 `divinebeasts-backend-local` Docker 网络。GatewayService 通过 Docker 服务名访问 `http://identityservice:8081`、`http://playerdataservice:8082` 和 `http://matchservice:8083`，而不是依赖主机端口。Compose 还将工作空间 `Shared/Contracts` 只读挂载到 Gateway 容器的 `/contracts`，并设置 `DIVINEBEASTS_SWAGGER_CONTRACTS_ROOT=/contracts`；该配置仅用于本地文档服务。

## 3. 前置条件

1. Windows 已安装并启动 Docker Desktop，且 `docker info` 可以返回服务端版本。
2. Docker Compose V2 可用，且首次构建时可拉取 `golang:1.23` 基础镜像和 Go 模块依赖。
3. 主机端口 `28080`、`8081` 至 `8084` 未被其他进程占用。GatewayService 使用 `28080`，以避免与本机已有的 `8080` 服务冲突。
4. 不需要在主机安装 Go；镜像构建使用固定的 `golang:1.23` 容器工具链。

本地部署不会读取 `Backend/configs/production.env.example`。该文件只描述生产必需的 PostgreSQL、Redis、NATS、Agones 和转移票据密钥；这些环境变量不得用示例值部署到生产。

## 4. 一键启动

从工作空间根目录执行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\Deploy\Local\StartBackendDevelopment.ps1
```

脚本会执行以下步骤：

1. 确认 Docker Engine 可用。
2. 使用 `Deploy/Docker/docker-compose.backend.local.yml` 构建五个最小静态 Go 服务镜像。
3. 以后台模式启动五个服务，并保留现有容器网络的正确重建关系。
4. 在可配置的 120 秒内轮询五个 `/health/ready` 端点与 `http://127.0.0.1:28080/swagger/`。
5. 超时时输出最近 200 行 Compose 日志并以非零退出码结束。

如首次构建时间超过默认值，可延长等待窗口：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\Deploy\Local\StartBackendDevelopment.ps1 -StartupTimeoutSeconds 300
```

## 5. 部署验证

执行结构与配置验证：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\Tests\Deployment\ValidateBackendDevelopmentDeployment.ps1
```

执行运行态验证：

```powershell
Invoke-WebRequest http://127.0.0.1:28080/health/ready
Invoke-WebRequest http://127.0.0.1:8081/health/ready
Invoke-WebRequest http://127.0.0.1:8082/health/ready
Invoke-WebRequest http://127.0.0.1:8083/health/ready
Invoke-WebRequest http://127.0.0.1:8084/health/ready
Invoke-WebRequest http://127.0.0.1:28080/swagger/
```

五个就绪端点应返回 HTTP `200` 和包含 `status: "ready"` 的 JSON；Swagger 页面应返回 HTTP `200` 的 HTML。服务版本可通过相同端口的 `/version` 查询；存活检查使用 `/health/live`。

本地接口文档地址：

```text
http://127.0.0.1:28080/swagger/
```

原始 OpenAPI 文件通过 `http://127.0.0.1:28080/swagger/specs/` 提供，例如 `GamePlatform/OpenAPI/gateway.openapi.yaml`。完整使用与安全边界见 `Docs/Backend/API与Swagger使用说明.md`。Swagger UI 前端静态资源来自浏览器访问的 `unpkg.com`；若该站点不可访问，页面仍提供 YAML 原始文件链接，可导入本地兼容工具。

## 6. 日志、状态与停止

查看容器状态：

```powershell
docker compose --project-directory . -f .\Deploy\Docker\docker-compose.backend.local.yml ps
```

查看全部日志或单服务日志：

```powershell
docker compose --project-directory . -f .\Deploy\Docker\docker-compose.backend.local.yml logs --tail 200
docker compose --project-directory . -f .\Deploy\Docker\docker-compose.backend.local.yml logs --tail 200 gatewayservice
```

停止本地环境：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\Deploy\Local\StopBackendDevelopment.ps1
```

停止脚本只停止并移除本项目 Compose 创建的容器和网络，不附带 `--volumes`，不会删除 Docker 卷或镜像。

## 7. 常见问题

| 现象 | 排查与处理 |
| --- | --- |
| `Docker Engine 不可用` | 启动 Docker Desktop，等待 `docker info` 成功后重试。 |
| 端口绑定失败 | 使用 `Get-NetTCPConnection -LocalPort 28080,8081,8082,8083,8084` 查找占用进程，停止冲突服务后重新启动。 |
| 就绪超时 | 运行 Compose 日志命令；检查镜像构建失败、端口冲突或主机防火墙策略。 |
| Gateway 请求下游失败 | 确认 Identity、PlayerData、Match 三个服务处于运行状态，并检查 Compose 内部服务地址未被覆盖。 |
| Swagger 返回 `404` | 确认 Compose 的 GatewayService 配置了 `DIVINEBEASTS_SWAGGER_CONTRACTS_ROOT=/contracts`，并以只读方式挂载 `Shared/Contracts` 后重新执行启动脚本。 |
| Swagger 页面未渲染交互界面 | 检查浏览器到 `unpkg.com` 的访问；网络受限时直接下载页面列出的 OpenAPI YAML 并导入本地工具。 |
| 需要持久化或外部消息 | 不应修改本地装配伪装成功；应改用生产装配并按下一节的生产门禁准备依赖。 |

## 8. 生产部署前置门禁

本仓库当前没有 Kubernetes 清单、生产镜像发布流程、Secret 注入、数据库迁移编排、NATS Stream 配置或 Agones 集群连接证据。因此不得把本地 Compose 成功宣称为生产上线。

生产部署至少需要：锁定并验证 `productiondeps,grpcdeps` 构建；注入 PostgreSQL、Redis、NATS、Agones 和转移票据密钥；执行迁移与备份/回退演练；验证 HTTP/gRPC 健康检查、观测、网络策略和服务账户权限；完成真实专用服务器与后端准入联调。以上每项均需独立的目标环境、授权、变更单和验证证据。
