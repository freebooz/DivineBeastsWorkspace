# 业务后端与共享代码工程化审查报告

> 历史静态审查快照：本文中的Git、工具环境和部署目录状态已发生变化。当前生产就绪结论及实际测试证据请阅读[业务后端生产就绪审查（2026-09-21）](业务后端生产就绪审查_2026-09-21.md)，不要将本文的早期环境描述用于当前发布判断。

版本：V1.3.0  
审查日期：2026-09-21  
审查范围：`Backend/`（Go 业务后端）与 `Shared/`（跨语言共享契约、生成配置及 C++ 绑定元数据）  
审查方式：目录与源码静态审查、配置与契约格式校验、生成物映射核对、可用工具链探测；**不等同于 Go 编译、单元测试、集成测试、性能测试或生产验收**。

## 1. 审查结论

当前后端和共享层已经具备可继续开发的工程基础，但**尚不满足“业务服务端和共享代码已完善、可按工程实践落地或发布”的要求**。

基础层已有明确分层、五个薄服务入口、生产依赖构成、测试骨架、契约版本锁和中文说明；不过正式 Proto／OpenAPI 生成产物全部缺失，`grpcdeps`（gRPC 依赖构建标签）代码已导入这些不存在的包。与此同时，`go.sum` 为空，本机没有 Go、`protoc`（Protocol Buffers 编译器）或 `oapi-codegen`（OpenAPI Go 生成器），也没有统一构建、部署、跨系统测试和工具脚本。因此不能证明普通 Go 构建、生产 HTTP 构建、生产 gRPC 构建、契约生成、数据库／缓存／消息集成或部署可重复通过。

工程状态应定位为：**后端基础纵向切片与契约治理已建立，尚未闭合为可发布后端**。

## 3. 已具备的工程基础

### 3.1 后端结构与边界

1. `Backend/cmd/` 有且仅有五个薄入口：`gatewayservice`、`identityservice`、`playerdataservice`、`matchservice`、`gameservercontrolservice`。`Backend/tests/architecture_test.go` 对该布局及生成目录所有权有结构门禁。
2. 领域、应用编排、传输适配、数据库、缓存、消息设施已经分层。生产基础设施使用 `productiondeps` 标签，gRPC 传输使用 `grpcdeps` 标签；本地组合与生产 HTTP／gRPC 组合已在文件结构上隔离。
3. `Backend/tests/production_composition_test.go` 已对 PostgreSQL、Redis、NATS JetStream、Agones、事务发件箱、防重放 `SetNX` 和 `FOR UPDATE SKIP LOCKED` 等关键生产实现片段设置静态门禁。
4. 身份、玩家资料、组队、匹配、比赛、服务器控制和跨服票据等核心一期领域已有实际源码；例如匹配领域明确覆盖 1v1 至 5v5、单排与组队容量校验，服务器控制领域限定 OpenWorld、Village、MainArena 三类正式角色。

### 3.2 共享契约与版本治理

1. `Shared/Docs/contract-version.json` 的当前契约版本为 `1.3.0`，后端模块身份为 `divinebeasts/backend`。
2. `Shared/Docs/codegen-tools.lock.json` 锁定 `protoc 30.2`、`protoc-gen-go 1.36.8`、`protoc-gen-go-grpc 1.5.1`、`oapi-codegen 2.4.1` 和 Go `1.23.0`；其中运行时依赖版本与 `Backend/go.mod` 的直接依赖一致。
3. `Backend/tests/contract_compatibility_test.go` 已检查契约版本、兼容矩阵、关键 Proto 字段、三服务器角色约束和 OpenAPI `operationId` 唯一性。
4. 已存在的生成元数据（Go ContractVersion／目录、C++ ContractVersion／目录／项目 Catalog）与 `Shared` 的版本文件构成了轻量静态约束。

### 3.3 配置与中文工程说明

`Backend/configs/production.env.example` 将数据库凭据、跨服票据密钥等敏感值保留为注入占位符，未把个人路径写入源码。后端领域代码、测试名和配置示例存在中文职责说明，便于审阅。

本次审查同时把全局“准确命名、标准惯例、中文注释与说明同步维护”规则写入 `AGENTS.md` 和《解决方案总体规划》。今后 Backend、Shared、UE、脚本与测试代码均须遵守该规则；详见 `AGENTS.md` 的“全局工程代码命名、中文注释与说明规范”。

## 5. 必须闭合的验证链

以下步骤是建议的执行顺序；涉及生成物、依赖锁或部署配置的写入操作，必须在有版本控制的工作分支中执行并审阅差异。

1. 安装并固定 Go `1.23.0`、`protoc 30.2`、`protoc-gen-go 1.36.8`、`protoc-gen-go-grpc 1.5.1`、`oapi-codegen 2.4.1`。
2. 在 `Backend/` 生成依赖校验和，并以只读模式复验：`go mod download`、`go mod tidy`（审阅差异后）、`go test -mod=readonly ./...`、`go vet -mod=readonly ./...`；条件允许时再运行 `go test -race -mod=readonly ./...`。
3. 从 `Backend/` 执行 `go run ./internal/tools/contractcodegen -workspace-root=.. -official`，生成 Go Proto／OpenAPI 与 C++ Proto 绑定；随后执行 `go run ./internal/tools/contractcodegen -workspace-root=.. -check`，并确认七个生成目标不再缺失。
4. 分别验证本地、生产 HTTP 和生产 gRPC 组合：普通 `go test`，带 `productiondeps` 的测试／构建，以及带 `productiondeps grpcdeps` 的测试／构建。生产 gRPC 构建必须实际编译导入生成 Proto 包的适配器。
5. 建立容器化或等价的临时 PostgreSQL、Redis、NATS JetStream 与 Agones 测试环境，执行迁移、五服务启动、认证、资料读取、组队匹配、服务器分配、跨服票据防重放及事务发件箱集成测试。
6. 在根 `Build/`、`Deploy/`、`Tests/`、`Tools/` 创建受版本控制的真实入口，并在 CI 中记录工具版本、命令、退出码、产物清单与兼容性结果；不能只保留目录规划或 README。
7. 以每个业务领域的产品优先级为准，实施当前仅 `doc.go` 的领域，或在总体规划中明确其为二期预留并移出一期可交付范围。所有新增命名、注释、接口和中文文档遵循全局工程规则。

## 7. 审查结语

后端与共享层应继续沿用当前“契约真源 + 生成器 + 五薄服务入口 + 分层端口”的方向，但不能跳过生成物、依赖锁、可执行测试和自动化交付这四道门槛。完成第 5 节的验证链并将结果留存后，才能重新评估其是否满足工程代码实践落地与发布条件。
