# 神兽联盟业务后端生产就绪审查

审查日期：2026-09-21。审查基线：`main`，`650f08c6a085dfa06b1db76b1408c22556f9d2bc`，以及当时的实际工作区。审查开始时 `Backend/`、`Shared/`、`Deploy/` 无未提交差异；其他目录已有用户修改，本次保留。

## 1. 结论与适用范围

**当前业务后端不能满足神兽联盟正式生产实践，不建议承载真实玩家、长期账号资产或收费业务。** 当前定位是五服务本地开发骨架、部分领域规则与控制面纵向切片；Swagger 可阅读、容器存活和普通单元测试通过，都不能证明生产业务闭环成立。

审查覆盖五个 Go 入口、本地及生产 HTTP/gRPC 装配、认证与玩家资料、组队匹配、服务器注册分配与迁移、比赛结果、Redis/PostgreSQL/NATS/Agones 适配器、共享契约、部署配置和已有测试。结论来自实际源码、实际构建检查和五个隔离行为复现。未连接生产环境，未修改业务源码，未重启现有服务。

依据当前总体规划，验收主线为：稳定登录身份 → 玩家建档 → 创建/选择角色与资格校验 → 世界分配及准入 → OpenWorld/Village → 1v1～5v5匹配与MainArena → 权威结算 → 后端确认返回实例与安全落点。当前这条链路没有在运行装配中接通。

仓库旧《业务后端与共享代码工程化审查报告_V1.3.0》是早期静态快照，其中“没有Git仓库”“不能运行Go”“Deploy为空”等描述已不适用于当前基线。本报告以本次证据为准。根规则要求的独立《整合与交付说明》在本次检索中仍未找到；已读取总体规划、插件相关边界及现有交付文档，未用历史文本代替源码结论。

## 2. 发布阻断与高优先级发现

本报告的 P0 表示必须阻断正式发布；P1 表示影响核心业务正确性、可恢复性或运营能力，正式接入真实玩家前必须完成。编号用于跟踪，不代表实现顺序。

### R01 / P0：现有一键发布生成开发装配，生产构建不可复现

- 证据：[Backend.Dockerfile](../../Deploy/Docker/Backend.Dockerfile) 第12行未传 `productiondeps`；[composition_local.go](../../Backend/internal/app/composition/composition_local.go) 第1行以 `!productiondeps` 启用内存会话、自动玩家资料、内存组队和结果存储。
- `Backend/go.sum` 实测为0字节。生产 HTTP 和生产 gRPC 的 `go test -mod=readonly` 均因依赖校验和缺失退出1。`Backend/generated/proto/` 实际只有 `README.generated.md`，gRPC适配器却导入该目录下不存在的正式生成包。
- 影响：当前一键部署重启后丢失内存状态；不能把现有镜像重命名为生产镜像。补依赖之后仍必须继续验证生成代码和生产编译，不能推断后续自动通过。
- 要求：建立明确区分开发/生产的构建入口，从锁定工具链生成所需契约绑定并审阅依赖锁；在只读依赖模式编译五服务并记录镜像、版本、迁移和回退。生产启动增加防止误装配开发依赖的检查。

### R02 / P0：内部控制面缺少调用方身份认证与实例授权

- 证据：[gameservercontrol_server.go](../../Backend/internal/transport/httpadapter/gameservercontrol_server.go) 第16行创建裸 `ServeMux`，注册、心跳、排空、分配、签票、验票与结果提交没有认证中间件。生产HTTP装配直接使用这些处理器。
- [composition_production_grpc.go](../../Backend/internal/app/composition/composition_production_grpc.go) 第112行使用无认证配置的 `grpc.NewServer()`，第135行客户端使用 `insecure.NewCredentials()`，也没有服务/实例授权拦截器。
- 本次隔离HTTP处理器测试：不提供任何凭据，注册MainArena实例返回 `200 {"accepted":true}`。这证明应用层接受未认证调用；没有据此断言当前宿主防火墙或公网暴露状态。
- 影响：能访问内部端口的调用方可冒用GameServerID、登记连接地址、排空实例、申请迁移或提交结果。只验证请求体中的GameServerID和MatchID相等，不等于认证了服务器。
- 要求：可信服务身份、目标实例授权、网络访问策略同时落实。为Dedicated Server绑定可验证的实例身份，为注册/心跳/结果/票据分别限制调用角色；有凭据也不能操作其他实例。[gRPC官方认证说明](https://grpc.io/docs/guides/auth/)说明了TLS和调用凭据的集成方式。

### R03 / P1：生产登录没有稳定账号和首次建档闭环

- 证据：[identity/service.go](../../Backend/internal/modules/identity/service.go) 第60行 `LoginGuest` 每次生成新PlayerID。HTTP/gRPC身份适配器只支持guest，没有持久账号与凭据映射。
- [postgres/repositories_production.go](../../Backend/internal/platform/database/postgres/repositories_production.go) 第84行虽实现 `EnsureProfile`，但全仓Go源码检索只找到定义，没有运行调用。生产PlayerData读取找不到记录会报错，本地自动建档仓储掩盖了这一差异。
- Gateway返回RefreshToken，但运行路由没有刷新/退出接口；AccessToken默认15分钟，当前不能通过公开API延续原会话。
- 影响：同设备重复登录成为不同玩家；全新生产账号登录后不能自动取得长期资料，不能可靠恢复进度和权益。
- 要求：稳定Account/Player绑定、真实身份提供方验证、幂等建档编排、失败补偿，以及刷新、撤销和重新登录用例。

### R04 / P1：创建票据没有接通匹配开局，游戏主流程缺失

- 证据：[gateway/api.go](../../Backend/internal/app/gateway/api.go) 第125行开始仅注册登录、资料读取、创建Party、创建匹配票据四个业务路由。没有角色创建/选择校验、世界准入请求、匹配查询/取消、开局通知或赛后返回用例。
- [composition_production_http.go](../../Backend/internal/app/composition/composition_production_http.go) 第56行和gRPC对应装配只创建 `matchapi.Service`；Redis Ticket仓储只是按请求ID保存票据，没有运行队列消费者或Matcher。
- [matchservice/orchestrator.go](../../Backend/internal/app/matchservice/orchestrator.go) 第78行的 `NewOrchestrator` 调用只存在于测试，未在运行装配接入。`NewTicket` 返回 `searching` 后没有运行代码将其推进到已匹配、分配和进服。
- 影响：1v1～5v5的模式定义、名单校验、不可拆队分组算法存在，但用户通过当前API不能完成一局竞技；也不能完成规划要求的首次进入真实世界及有效返回落点。
- 要求：接通玩家主流程应用用例、匹配工作进程、状态查询/通知、取消与超时恢复、角色资格、版本兼容和安全出生点校验。分期实施可保留，但不能以领域单测替代端到端交付。

### R05 / P1：服务器注册表和分配记录仍为进程内状态

- 证据：[gameserver/gameserver.go](../../Backend/internal/modules/gameserver/gameserver.go) 第77行创建内存Registry；[gameservercontrol/service.go](../../Backend/internal/app/gameservercontrol/service.go) 第92、106行维护内存assignments。两个生产装配同样使用这些实现。
- 影响：多副本之间不共享注册、容量、比赛绑定；注册落到副本A后，副本B可能找不到实例/Assignment。控制服务重启后，仍运行的比赛失去后端分配记录，结果上报和迁移验证被拒绝。已有Redis防重放和PostgreSQL结果持久化不能恢复这些状态。
- 要求：明确控制面状态所有权、共享存储与原子分配、租约/代次、领导者或分片策略、实例重注册和任务恢复。必须验证控制服务重启及两副本负载均衡，不仅测试互斥锁。

### R06 / P1：世界容量存在准入窗口超分配和过期预留泄漏

- 证据：[gameservercontrol/service.go](../../Backend/internal/app/gameservercontrol/service.go) 第326行验票后调用 `CommitReservation`；[gameserver/gameserver.go](../../Backend/internal/modules/gameserver/gameserver.go) 第240行只减少ReservedPlayers，没有同时记录已准入但尚未由心跳确认的玩家。
- 本次复现：容量1的世界给玩家A签票并完成验票，下一次心跳之前状态为 `CurrentPlayers=0, ReservedPlayers=0`，玩家B仍可获分配。
- 另有反向问题：玩家拿到票据后断线/不连接，预留只是整数计数，没有按票据到期回收的租约记录；定期心跳不能可靠恢复这些未使用容量。`PlayerSlots`默认值也未统一传入签票失败补偿路径。
- 要求：用单次准入身份记录“预留、已准入待确认、在线、取消/过期”状态，原子迁移占用而非直接释放；处理迟到心跳、重复准入、票据超时及批量人数。

### R07 / P1：心跳失效没有阻止实例被继续分配

- 证据：[gameserver/gameserver.go](../../Backend/internal/modules/gameserver/gameserver.go) 第157行 `Allocate` 只筛选角色、区域、体验、状态和容量，不检查LastHeartbeat；未发现运行中的超时摘除工作进程。
- 本次复现：LastHeartbeat为24小时前但状态仍Ready的世界实例照常被分配。
- 心跳还能直接覆盖Status；未见严格的状态迁移规则保护Draining，后续Active心跳可能重新开放分配。World分配也没有BuildVersion/ProtocolVersion兼容筛选。
- 要求：配置化心跳租约、失联摘除、排空状态机、实例代次和版本匹配。修复后用失联、排空后旧心跳、进程替换三个用例验证。

### R08 / P1：匹配幂等键未按玩家隔离，重复入队约束不完整

- 证据：[matchapi/service.go](../../Backend/internal/app/matchapi/service.go) 第66行按客户端自报ClientRequestID全局查找，命中后直接返回，发生在Party所有者检查之前；Redis键也只拼接ClientRequestID。
- 本次复现：玩家A使用 `request-1` 创建票据，玩家B使用同一个请求ID收到A的票据与成员列表。相同玩家换模式但复用请求ID也可能得到旧请求结果，没有参数摘要冲突检查。
- 任意更换ClientRequestID可以重复为同一玩家建立活动票据；Party保存是无Revision条件的SET，锁名单和保存票据分步执行，失败补偿还吞掉错误，不能保证多副本并发下“一个玩家只处于一个匹配中”。
- 要求：至少以游戏、玩家、操作、请求ID作用域定义幂等键，并保存参数摘要；玩家活动票据唯一约束、Party Revision CAS、入队/锁名单/幂等结果原子提交。

### R09 / P1：成功结算后的重试被拒绝，结果内容校验不足

- 证据：[gameservercontrol/service.go](../../Backend/internal/app/gameservercontrol/service.go) 第344行先要求活动Assignment，首次提交完成后第366行删除该记录。下层 `ResultService` 的MatchID幂等读取因此无法在第二次调用到达。
- 本次复现：首次成功后重发完全相同的结果，返回 `GAME_SERVER_ASSIGNMENT_NOT_FOUND`。生产中“数据库已提交但响应丢失”会触发此路径。
- 同一入口只比对MatchID和ArenaModeID，未把结果中的Players/Teams与权威Roster逐项核对。`ResultService.Submit`只校验三个身份字符串，未校验比赛时间、参赛名单和胜者一致性。既有测试甚至允许没有Players/Teams的结果成功。
- 要求：持久化比赛及提交者绑定，鉴权后优先处理已完成比赛的幂等结果；不同载荷明确冲突。结果提交与服务器回收采用可恢复状态机，并验证全部权威名单及合理性约束。

### R10 / P1：消息发布有基础，但消费、契约与业务结算闭环缺失

- 证据：[postgres/repositories_production.go](../../Backend/internal/platform/database/postgres/repositories_production.go) 第136行确实在一个事务中写入结果与Outbox；这部分应保留。
- [match/result.go](../../Backend/internal/modules/match/result.go) 第110行构造扁平 `eventType/eventVersion/matchId/...` 消息，与 [message-envelope.schema.json](../../Shared/Contracts/GamePlatform/Events/Common/message-envelope.schema.json) 要求的messageId、messageType、gameId、environmentId、traceId、producer、payload等结构不一致。
- 未发现正式Stream/Consumer部署配置或消费处理器；没有消费幂等、奖励事务、Ack后故障恢复与死信重放实现。`rating`、`economy`、`commerce`、`inventory`、`entitlement`等仍只有领域边界说明。是否开放付费可分期，但未实现的能力不能作为生产功能使用。
- 本地ResultStore与本地Outbox Worker还使用两个不同的内存存储，结果产生的事件不会进入该Worker。
- 要求：统一事件真源及迁移版本，落实消费侧幂等与业务事务，按实际上线范围闭合结算/奖励。`WithMsgID`不能独自替代消费幂等；[NATS官方JetStream说明](https://github.com/nats-io/nats.docs/blob/master/nats-concepts/jetstream/README.md)明确说明发布或确认丢失时可能发生重投。

### R11 / P1：Readiness固定成功，无法支撑生产故障摘流

- 证据：[servicehost/handler.go](../../Backend/internal/app/servicehost/handler.go) 第26行无条件返回200和ready。虽存在 `health.State`、数据库Ping和Redis Ping，宿主没有把它们接入就绪判断。
- 影响：依赖断开、gRPC下游不可达、迁移未执行或消息链路不可用时，健康页面仍可能显示ready；此前“五个健康端点通过”只能证明HTTP处理器在工作。
- 要求：按服务职责注册必要依赖和启动屏障，设置检查超时与缓存，启动完成前和排空期间拒绝新流量。不要把依赖失败直接等同于进程应重启；[Kubernetes官方探针说明](https://kubernetes.io/docs/concepts/workloads/pods/probes/)区分了存活与就绪的职责。

## 3. 还需在生产化中处理的工程问题

以下来自源码静态检查，未通过真实基础设施注入故障验证，不能表述为已完成环境复现：

- **Redis令牌轮换不是原子条件更新。** `SessionRepository.Save`先读旧会话、删除旧索引，再事务写新会话，且删除错误被忽略；并发刷新可留下旧索引，`byIndex`又不核对所查Token是否等于当前会话Token。公开刷新接口尚未接通，在开放前必须修正并发与撤销语义。
- **公网请求保护不足。** Gateway直接对Body做JSON解码，没有请求体上限或限流；错误映射把下游故障泛化为401/404，部分错误内容直接向外返回。需要按部署网关与服务的真实边界实现限流、超时、大小限制和可诊断的错误分类。
- **Agones分配失败补偿缺失。** 外部Allocation成功但Registry确认失败时没有回收/协调任务。默认客户端没有在生产装配中加载Kubernetes ServiceAccount CA；现有scratch镜像也未携带CA集合，应完成真实TLS连接和证书轮换验证，不能靠测试HTTP服务证明集群可用。
- **Outbox失败处理不完整。** 每批顺序发布，遇到首条失败便返回；其余已领取消息等待租约到期，没有按消息退避、死信或人工恢复流程。需验证毒消息不会长期阻塞正常事件。
- **生产交付证据不足。** 当前Deploy主要是本地Compose及启停脚本；没有可核验的生产依赖拓扑、备份恢复演练、生产迁移门禁、发布回滚与容量/SLO基准。仓库外是否存在平台能力本次未知。
- **所谓生产组合测试主要检索源码字符串。** `Backend/tests/production_composition_test.go`以 `strings.Contains` 验证接线、SET NX和SQL关键字，不能证明事务、集群并发与网络恢复正确。

## 5. 保留的有效基础与修复顺序
