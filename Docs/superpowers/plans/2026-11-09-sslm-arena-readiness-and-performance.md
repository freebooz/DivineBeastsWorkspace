# SSLM 竞技场转场与性能整改计划

> 实施按 `superpowers:executing-plans` 的顺序逐项验证。基线为 `main/57a139ec`，在当前工程内增量实施和留证。

目标是让双人竞技从新手村报名、进场、开战、结算或主动退出，到返回原排队位置都可判断当前状态，并降低已定位的客户端及匹配路径开销。

## 1. 竞技场转场准备状态

- [x] 用现有转场操作 ID 关联准入、正确地图、参赛角色就绪和战斗放行。复用竞技 `GameState` 的阶段通知与服务端截止时间，分别覆盖等待参赛者、倒计时和同步角色。
- [x] 竞技客户端向应用流程提供只读准备状态，应用流程核对当前操作、地图、体验和准入后交给既有加载页显示。取消、失败和切图清理各自作用域，输入放行沿用服务器原有倒计时和参赛资格。
- [x] 原生回归覆盖准备阶段推进、加载页投影、旧状态清理和战斗资格边界。
- [ ] 双客户端真实进场、结算、主动退出和断线恢复。

## 2. 名称板事件热路径

- [x] 在 `GamePlatformWorldUIService` 区分单实体投影和镜头／视口刷新。单实体按 ID 直接查找，全量刷新保持重入保护。
- [x] 将位置更新与内容投影分开，在 `GamePlatformWorldWidgetBase` 只为首次显示、重显和真实内容尺寸变化执行即时预排版。项目名称板优先取角色胶囊锚点，原生回归覆盖静止视图、移动、隐藏、本人排除及同步注销。

## 3. 生产匹配存储

- [x] Redis 真实适配器分批监听和读取成员索引、队伍键，保留事务快照、队伍锁、用户预留、过期及重试。隔离 Redis 通过事务、通知和故障恢复回归。
- [x] 按持久状态及当前租约减少同阶段重复投影，通知送往受影响的观察者。10、100、1,000 票据的本机快照读取与复核分别由 220、2,200、22,000 次往返降到 6、10、88 次。原始结果见 `Saved/Validation/SSLMPerformance20261109/Backend/Final-benchmark.log`。
- [ ] 单独验证候选调度、跨场锁、订阅连接容量和真实部署负载。当前本地后端继续使用已运行的版本。

## 4. 代表技能 Niagara 伸缩

- [x] 用 Monolith 核对火球、冰箭和奥术九个 System 的引用及裁剪策略。火球与冰箭飞行复用 `ET_VFX_ProjectileTrail`，配置写入既有表现定义，已保存、独立重读并验证只进入客户端包。
- [ ] 其余五个待补 System 的现成候选会整体裁剪关键表现，须先验证低档保留预警和方向，再接入合适的 Effect Type。四档及 5v5 GPU 预算仍待采样。
