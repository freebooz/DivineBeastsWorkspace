- 正常、失败、取消、越权、重试、断线、世界退出、资源缺失和多实例的回归材料及中文说明。

本次不实现长期战队、排位段位与赛季奖励、单排轮斗、观众系统、跨区好友搜索、聊天、魔兽职业／装备／经济系统，亦不复制暴雪纹理、图标或品牌资源。采用普通非评级练习赛作为首个完整闭环；评级入口不提供固定分数或假成功占位。

## 组队交互

### 目标菜单与邀请

玩家左键选中合法可见目标，右键目标或头像打开菜单。对自己、NPC、无公开玩家身份的目标不显示玩家组队操作；目标身份由当前受控角色与服务器提供，不能把Actor地址或可编辑昵称作为授权依据。

无队伍时“邀请组队”命令在后端完成资格校验后，原子建立唯一普通队伍并发送邀请；有队伍时仅队长可邀请。对方已在队伍、已进入不允许变更阶段、离线、拒收或不具备可见资格时返回对应错误，不伪造邀请成功。

邀请弹窗显示邀请者、当前成员数、活动和有效剩余时间，提供接受／拒绝。接受时再次校验邀请仍Pending、目标本人、队伍版本、容量与玩家唯一队伍索引，原子完成入队与邀请终态。并发接受多个邀请只允许一个成功，其他返回已入队；重复点击返回原结果。

### 申请加入与成员管理

未入队玩家可通过目标菜单向该玩家所在、允许申请的普通队伍提交申请。申请面板只对有管理权的队长可见；接纳并不直接修改本地名单，而等待后端新快照。申请不预占名额，批准时复核申请者当前队伍、在线状态、队伍锁及剩余容量。

队长可批准／拒绝、邀请、移除成员、转让队长和解散；普通成员可设置自己的准备状态及离队，不能修改别人。未排队时队长离队：有其他成员则按最早加入顺序转让，无其他成员则解散；同一加入顺序冲突属于存储错误，不能依赖map遍历选队长。显式解散需二次确认。

名单、活动或队长变化使原准备确认失效。邀请、申请取消与超时均有独立终态。队伍锁定时禁止增删成员、转队长及改模式；有离队意图先请求取消整队匹配，等后端确认解除锁后再离队，不允许本地先解锁。

在线状态来自可信会话／连接租约，不允许客户端修改Member.Online自证在线；正常跨服不会因旧World退出而立即被判离线。队长离线先保留60秒重连宽限，仍未恢复且队伍可编辑时按最早加入的在线成员转让；仍在队列／确认阶段时，先完成取消并解除锁再转让。迁移已提交或局内保持原名单及队长身份，待比赛终态解锁后处理，不借自动转让绕过名单锁。全员离线时保留到队伍TTL清理，成员重连需读回真实状态，不能沿用本地队长标记。

### 小队面板

显示至多5名真实成员、队长标识、在线／断线、角色展示、准备状态、当前活动、队伍锁及本人可执行操作。一般好友列表继续沿用原有256项保护；与本功能无关的好友系统不扩展。

键鼠支持悬停说明、清晰禁用原因、Tab导航、Enter确认与ESC关闭普通面板。ESC或关闭按钮不等于拒绝邀请、取消匹配或离队；涉及业务状态的动作必须显式提交命令。弹窗结束后恢复原焦点，输入捕获不穿透到移动／施法，沿用GamePlatformInput与CommonUI仲裁，不复制光标控制器。

## 匹配与入场状态

状态流为：可报名 → 小队准备确认 → 排队 → 找到比赛待逐人确认 → 分配实例 → 取得准入 → 加载／迁移 → 竞技准备 → 对战 → 结果提交 → 安全返回。单人跳过小队准备确认，不要求先创建普通队伍。

多人小队由队长发起准备确认，全员对同一名单版本、模式和区域确认后才能进入队列。小队人数超过所选单队容量直接拒绝，不自动踢人或拆队。未满小队与单人都可补齐；不强制治疗／坦克职业构成，角色偏好不得伪装成硬性职业限制。

匹配服务按游戏、模式、区域和兼容规则／内容版本隔离队列，原子预留候选票据后组成两支完整队伍。已有partitionTickets可复用精确分队，但生产消费必须增加候选数量上限、公平等待及租约恢复，不能扫描整个Redis队列进行无限回溯。候选无法完整分队则继续等待，禁止拆队或用机器人补齐真实玩家名额。

每个玩家同时最多拥有一个有效排队／比赛预留；1v1不接受多人队伍。首版非评级匹配不向客户端开放隐藏分输入，也不引入假MMR。匹配等待时间显示真实已等待时长，无统计模型时不展示虚构预计等待时间。

报名还需后端确认本人处于允许报名的Village／OpenWorld就绪会话，不允许迁移中、局内或旧会话再次排队。队伍名单从入队列锁定至候选取消或比赛结果终态确认；正常跨服不解锁，比赛名单快照始终独立于可编辑的普通队伍。

找到比赛后，全体参赛者分别接受／拒绝，队长不能代替队员接受。全部接受后才进行竞技场分配；有人拒绝或超时，本次候选取消，各原子队伍回到可报名状态，不自动把部分玩家送入竞技场或静默重新排队。

取消与匹配成功以版本条件竞争：预留提交前取消成功；已进入确认阶段则走拒绝确认；迁移已提交后返回明确的阶段冲突并读取最新状态，不能承诺撤销已经发生的跨服。队长取消作用于整队；普通成员离队意图通过整队取消事务处理，不能只删除自己的索引而留下其他人锁死。

匹配成功不等于可以立刻切图。必须取得受信Assignment、真实Ready实例、匹配的角色／Session／ServerBoot／规则与内容版本，以及本人一次性TransferTicket后，交给现有ApplicationFlow、Loading和Session进入链。Widget不得直接OpenLevel、拼接连接地址或保存准入令牌。

## 权威歼灭与重连

竞技运行层为当前MatchId持有名单中的参赛者状态：存活、已淘汰、退出／超时；连接状态独立，断线不直接等于死亡。队伍存活数由服务器事实维护并复制，不从客户端生命条或在线图标推算。

现有评分／胜负接口接入GameMode，策略身份必须解析为真实受支持实现，未知策略拒绝初始化。项目配置选择单局歼灭策略；通用积分与复活机制保留给明确选择它的现有测试／模式，不能全局删除或把PolicyId只作为装饰字段。

死亡处理先验证事件ID、比赛、玩家、当前Pawn及出生代次，再一次性标记淘汰、失活玩法资格并记录统计。已淘汰不发复活请求；重连、换Controller、重新出生及技能复苏入口都不能将淘汰者恢复为可战斗状态。项目本局不提供技能复苏，避免绕过“死亡后退出本局”的规则。

胜负检查在本服务器帧的权威战斗事实处理完后合并执行一次，不在首个死亡委托中立即关局。只有一队仍有存活者则该队胜；同一权威帧双方存活数都为零则平局。不创建常驻Tick扫描名单；仅有死亡／退出等变更时安排一次帧末检查，世界退出取消该任务。

环境伤害、自伤或没有击杀者的死亡仍计入淘汰。重复事件以及同一出生代次的重复死亡不重复扣人数。比赛已结束后的迟到伤害不改变胜负和结果修订。

断线时保留服务器Pawn或等价权威生命状态，不销毁后满血重建；短暂失联不能获得躲避伤害的收益。宽限内死亡则重连仍是淘汰状态，已结束则只恢复结果视图。重连票据必须重新验证目标比赛与实例，不重用旧票据。单人主动弃权仅令自己退出本局，不能让普通队长代表其他成员整队投降。

死亡观看只允许已授权的友方视角与已复制信息，不提供自由相机透视敌方。服务器崩溃、版本不兼容或未齐员属于取消／故障，不伪造正常获胜和奖励。

## 后端事务与接口扩展

跨UE／Go的公开请求及快照以`Shared/Contracts/GamePlatform/OpenAPI`为真源，项目角色／世界扩展归`Shared/Contracts/Games/DivineBeasts`；内部RPC扩展位于`Backend/internal/contracts/proto/match-service.proto`。保留已有路径、字段号与枚举号，通过锁定生成器产生绑定，不手改生成物。

在现有`POST /v1/party`和`POST /v1/matchmaking/tickets`基础上增加以下操作合同。具体请求／响应字段由后续实施计划细化进契约真源，不能仅在客户端手写一个可联网的同名对象。

| 领域 | 必须提供的操作 | 授权和版本约束 |
| --- | --- | --- |
| 普通队伍 | 当前队伍查询、成员准备、离队、移除、转让、解散 | 主体来自认证会话；本人和队长权限分别校验，写操作绑定预期Revision。 |
| 邀请 | 创建、本人待处理查询、接受、拒绝、撤回 | 仅邀请目标可接受／拒绝，发起者在仍有权限时可撤回。 |
| 申请 | 创建、本人取消、队长查询、批准、拒绝 | 不公开其他玩家的申请列表；批准需再次确认目标没有入队。 |
| 匹配 | 创建、本人状态、整队取消、逐人入场接受／拒绝 | 一人一有效预留，状态迁移用版本条件，票据ID不能代替权限。 |
| 观察 | 带作用域与游标的增量状态及完整重同步 | 仅返回本人有权限的数据；游标过期明确要求重同步。 |
| 准入／返回 | 本人迁移状态和新准入、赛后返回确认 | 无客户端自选目标地址；不在公共队伍事件中广播TransferTicket。 |

每个写命令使用认证主体、游戏、操作种类和ClientRequestId组成幂等域，存储标准化请求摘要。相同主体、同键、同内容返回已提交结果；同键不同内容冲突；不同主体同键互不命中。超时只代表结果未知，客户端先读状态，再用原键安全重试，不能自动发新键创建第二条队列。

Gateway与领域服务共同限制请求正文、标识长度、待处理邀请／申请数量和命令频率，配置必须有有限正上限；超限返回可识别错误及适用的重试时间。名单查询仅对成员或该操作明确授权的邀请／申请参与者开放，不能通过递增PartyId遍历其他队伍或泄露其私有信息。

队伍成员索引、邀请终态、人数、Revision、小队锁、票据及玩家有效预留由Redis事务／Lua原子更新，不使用进程内互斥代替多进程一致性。首版生产使用现有单逻辑Redis写域；检测不支持跨键原子操作的部署时拒绝启用该功能，不静默退化为多次SET。未来Redis Cluster需独立分区合同，不在本次声称已经支持。

队列候选持有有期限的所有权和递增栅栏代次。工作进程重启后按后端状态恢复／释放过期预留，不依赖某个Go进程的内存goroutine维持匹配真源。Redis不可用时明确不可报名；TTL过期必须同步处理成员索引和锁，不把TTL当作完整业务清理。

分配、签票、结果和返回属于跨服务操作，不能假装Redis事务可以包住全部服务。比赛编排增加持久操作记录及可恢复步骤：创建意图、分配完成、签票、提交或撤销；使用现有PostgreSQL与事务发件箱设施，消费端按操作身份及修订幂等。跨Redis／数据库边界通过持久步骤与补偿恢复，不做无法实现的跨库原子成功承诺。

部分签票失败不得向部分玩家发布可用入场成功；撤销已签票、撤销候选并排空闲置实例。清理失败记录重试状态和告警，不吞掉错误；已经消费票据的迁移失败转入真实恢复／返回流程，不能重新塞回原票据。

内部HTTP与grpcdeps调用必须具备同等权限、字段校验、截止时间和错误语义，生产HTTP／gRPC组合根都接入真实实现；不增加第六个Go入口。客户端只调用Gateway，不直接访问Redis、内部Match或控制面。

## 事件更新与界面生命周期

组队和匹配使用完整快照加递增事件游标。首版通过平台在线适配的有界长轮询订阅交付，服务端最长等待20秒，每个已认证客户端只保留一个活动观察请求；20秒为传输提案，不是Widget刷新频率或性能达标数据。

状态变化即返回，空响应续接；故障按有上限的退避重连，未恢复时显示状态未知且禁用危险动作。UI不Tick查询业务状态，不设置每秒GET队伍／匹配的计时器。邀请、Buff、施法和倒计时的显示只依据权威截止时间进行有界本地展示更新，不据显示归零自行提交权威终态。

事件绑定SourceScopeId、会话代次、聚合身份及Revision，迟到旧账号、旧队伍、旧匹配事件不写入当前视图。完整重同步和订阅切换需无缝衔接游标，防止先读快照后订阅丢事件。发出的事件具有可恢复身份，不能把普通C++委托当成跨网事件总线。

截止时间快照同时携带服务器时间基准，显示剩余时间使用本地单调时钟估算并在新快照到达时校正，不依赖可被用户调整的系统时钟。高频GAS／施法／生命变化走既有复制事实与本地事件，不挤入组队HTTP观察通道。

页面关闭只撤销页面拥有的订阅与输入，不取消队伍本身；认证退出则先失效所有账号作用域回调，再清空本地视图并执行后端退出规则。清理、命令完成和状态广播可能同步重入，回调必须验证弱对象、请求身份及代次。取消本地等待不等于后端事务回滚。

## 真实界面与地图资产

公共邀请／申请／队伍面板资产归`DBAUIPack_Core/Content/UI/Social/`，父类由DivineBeastsUIClient提供；竞技模式、入场确认、敌方框架和结果资产归已有`DBAArena/Content/UI/`，不让公共UI内容包引用竞技专有父类。现有PartyRoster与Buff／施法等部件先检查真实Widget树及绑定再复用，不凭文件名认定已可交互。

所有Widget Blueprint布局、命名控件、状态样式、焦点、导航和动画修改均使用Monolith MCP。开始资产动作前核对锁定UE5.8、正式`Game/DivineBeastsArena.uproject`、服务版本、动作目录和实际可加载C++父类；新增父类没有匹配DLL时不得通过假父类继续制作。

逐资产执行编译、保存、关闭／重开与结构回读，并在所属插件`Docs/MonolithGenerationManifest.json`登记。当前不启动构建／LiveCoding；编辑器无法加载新类型时保留源码和明确资产阻塞，等待用户统一构建，不能宣称界面已交付。

优先复用现有玉石主题、九宫格和按钮状态，不另造一套粗糙金属魔兽贴图。新导入彩色资源必须执行导入阻断审计与当前源指纹RHI比对；禁止Monolith 0.23.0的widget预览PNG路径，禁止为其Gamma错误调暗原稿。键鼠、不同视口、安全区、中文可读性、焦点及可访问性分别核验。

真实竞技地图目标归`DBAWorldPack_MainArena`。只有引擎创建并保存地图、双方各至少5个合法出生位／准备区、权威碰撞、导航及世界／体验定义后，才登记真实内容包、主资产扫描与组合；禁止建立空包或文字地图。五模式可复用同一竞技白盒地图和不同出生子集，不复制五套服务器或地图逻辑。

本规格不指定虚构的已存在MapId、主资产ID或内容哈希。地图生成后由真实定义给出稳定身份及ContentRevision，再与UE模式、Go配置和Assignment交叉校验；任一缺失维持不可报名。正式技能和权威资源未批准时只能进入明确开发配置，不能标记ProductionReady。

## 结果与返回

UE仅接受权威比赛事实并生成绑定MatchId、ServerBoot和结果修订的结果；后端验证可信服务器、Assignment名单与幂等键后提交。重复提交返回同一结果，不重复发奖；首版不添加经济奖励或评级写入。

客户端区分“比赛结束”“结果提交中”“结果已确认”“返回处理中”。返回由后端重新选择有效Village／OpenWorld实例和合法安全落点：原Village仍可用时优先返回；不可用时按现有项目世界准入规则重新分配。不得把旧地址、旧票据或原Pawn坐标当成安全返回证明。

结果提交失败、返回失败分别可恢复，不能因结果未确认直接把玩家丢回登录或销毁实例。MainArena只有在结果已持久化或明确故障终态、所有玩家完成迁出／释放且资源清理结束后，才完成Drain／Shutdown。现有Agones实施记录指出最终回收调用仍有缺口，实施时须核对其最新源码并接通既有控制面流程，不在另一处重新造回收器。

## 验收合同

| 范围 | 最小输入与预期 |
| --- | --- |
| 邀请与申请 | 接受、拒绝、撤回、超时、满员、已入队、被锁、无权限；两并发邀请只入一队，失败不增加成员。 |
| 成员管理 | 队长转让／离队／解散，普通成员不得修改他人；名单变化使准备失效，锁定时不能越过取消事务。 |
| 幂等与并发 | 不同主体同键隔离，同主体同键异参冲突；多进程创建／取消／批准竞争、Redis失败和补偿失败可恢复。 |
| 五模式 | 各模式单排、满队、部分队伍补齐、超员拒绝；每队精确N人、总数2N、原子队伍始终同队。 |
| 匹配确认 | 全员确认、拒绝、超时、取消与候选竞争、工作进程崩溃恢复；无“创建票据即匹配成功”。 |
| 分配与准入 | 无就绪实例、版本错、角色不合法、部分签票失败、旧／重复票据、名单外玩家全部拒绝并留下清理状态。 |
| 单局歼灭 | 五模式逐一覆盖无复活、环境死亡、同帧双方死亡平局、重复死亡、迟到事件及时间到平局；不按击杀阈值结束。 |
| 重连 | 存活者重连不满血、不换英雄；断线期间死亡、死亡者重连、超时退出、比赛结束后重连均不复活。 |
| 结果与返回 | 重复结果不重复提交，后端拒绝伪造结果；原村实例失效则新分配，返回失败重试不用旧票据；完成后实例可排空。 |
| 三层与端侧 | 关闭竞技仍可组队／登录／进入Village与OpenWorld；Server不依赖公共客户端，不Cook纯UI／VFX与开发地图。 |
| 生命周期 | 多World、账号切换、重复结束、旧代次、观察游标丢失与重同步、页面关闭、世界退出，不串号、不留下计时器或租约。 |
| UI与资产 | 真实Widget父类／命名控件／焦点／输入捕获／中文错误，编译保存重载与源图RHI一致；三维地图出生、碰撞与准备门禁由引擎核验。 |

Go测试放对应包，生产Redis／PostgreSQL适配必须用真实依赖的集成场景补证；内存仓储仅作明确标注的测试替身。UE测试放实际模块Private/Tests，接口和权威行为优先可复现回归，不把纯文本搜索当成运行验证。

后续验证沿用已存在的`Tests/Architecture/ValidateDesignBaseline.ps1`、`Tests/Architecture/TestEnglishProjectNames.ps1`、插件组合与继承边界门禁；UI颜色沿用`Tests/Assets/AuditUIColorImportedAssetsMonolith.py`与`Build/Game/TestUIColorRHI.ps1`。新增场景需要扩展真实测试，既有入口存在不代表本功能覆盖已通过。

按当前“不构建”约束，本阶段不运行UE／Go编译、LiveCoding、Cook、Stage或自动化游戏进程。后续统一构建后分别运行Editor、Client、Server、Go测试／vet／适用的race、双客户端／专服联调、五模式、干净Cook及服务器产物审计，最后集中人工核验。未执行项必须保留未验证状态。

## 兼容与交接

不重命名既有插件、模块、反射类型、模式GameplayTag、主工程和协议身份。新增字段采用兼容演进；改变接口会影响现有测试替身、HTTP与gRPC适配及所有调用方，实施计划必须逐项列出。

规则和内容修订共同发布，客户端旧版本不得进入不兼容比赛。回退先停止新报名，排空本规则的进行中比赛，再回退业务与配置；不删除结果历史，不为回退复用协议编号或旧票据。

本规格审阅通过后再生成书面实施计划，按契约／原子业务、真实队列与准入、规则执行、客户端与Monolith资产、统一验证五个相互衔接的工作包安排文件所有权和测试顺序。Native、不创建工作树和不构建的用户约束继续有效；书面计划仍须审阅，不把本次方向确认等同于尚未生成的计划批准。
