## 1. 目标、范围与规范来源

开发者从唯一正式工程 `Game/DivineBeastsArena.uproject` 的受控开发入口进入演示中心，不必先登录、创建角色或进入正式世界。每个真实插件都有独立菜单，每项受支持的功能都能找到实现依据、案例、操作、预期结果、缺口和人工结论。相关案例允许共享地图，但不共享或自动继承“通过”结论。

本规格覆盖开发演示编目、UI、关卡复用、调用适配、生命周期、证据和人工签收；不扩展插件的业务规则，不把演示系统变成第二套玩法执行器、资产管理器或后端。发现业务功能缺失时登记到对应插件整改项，禁止在演示层以假逻辑补齐。

规范来源：根 `AGENTS.md`、[解决方案总体规划](../../Architecture/解决方案总体规划.md)、[插件开发规范](../../../Game/Plugins/插件开发规范.md)、[整合与交付说明](../GamePlatformAuditRemediation/整合与交付说明_2026-10-09.md)、[UI 纹理视觉规范](../UITextureVisualPolicy.md)、[颜色链路规范](../UIColorPipeline.md)。发生冲突时以现行工程规则和用户最新明确指令为准。

范围包含现有 47 个代码插件及 18 个内容包。内容包属于项目层内部，不是第四逻辑层；外部引擎插件不是本次逐插件交付范围，其依赖和版本仍须记录。后续新增或退休插件必须重新扫描并更新编目，不把本次数量写成运行时上限。

## 3. 架构与所有权

| 所属位置 | 职责 | 明确不承担的职责 |
| --- | --- | --- |
| `GamePlatformUI` | 跨游戏页面、组件、层栈、焦点和输入契约 | 不引用 SSLM 资产、插件清单或项目规则 |
| `GamePlatformData` | 定义与资源加载、既有主资产身份和调用方租约 | 演示中心不另建资产管理器 |
| `GamePlatformDeveloperTools` | 中立编辑器入口、自动前置检查、人工审核与证据校验 | 不硬编码项目地图，不让开发客户端链接 Editor 模块 |
| `DBAClient/DivineBeastsDemoClient` | 项目开发目录、只读状态、导航及已允许的项目演示适配 | 不写生产账号/余额，不承载服务器权威，不硬依赖 MOBA |
| 对应 MOBA/竞技客户端组合位置 | 按开发配置注入竞技案例适配 | 不通过公共客户端反向加载竞技；不增加平行竞技框架 |
| `DBAUIPack_Core` 开发专用资源范围 | 项目演示 Widget、样式、主题及界面动画 | 正式 UI 不硬引用开发 Widget，服务器不 Cook 这些资产 |
| 既有开发地图及其真实内容所有者 | 场景组合、测试对象与可见资源 | 不复制正式插件源码或迁走其他包拥有的资源 |

平台能力独立核验使用中立数据与最小依赖配置；包含 SSLM 英雄、美术或项目规则的案例必须标记为“项目集成”，不能充当平台可复用性的唯一证据。MOBA 关闭时，基础目录、通用 UI 与世界案例仍可用。

只在现有正式工程内使用不同测试配置，不创建新的 `.uproject`、服务器角色或空插件。OpenWorld、Village、MainArena 仍是唯一三种服务器角色；教学和训练是 Village 体验。

新增项目控件优先继承已有平台稳定页面/组件契约。当前演示桥接直接继承 `UUserWidget` 的兼容关系，需要在实施时检查派生蓝图和命名控件；不得为了目录形式直接批量改父类。编辑器审核桥接只能在 Editor 条件内依赖开发工具类型，公共客户端头不得暴露它们。

## 4. 编目合同与唯一真源

### 4.1 四级关系

```text
Plugin（真实插件身份）
└── Feature（独立功能及实现依据）
    ├── Scenario（正常/失败/取消/清理等可执行案例）
    │   ├── Map / Surface（可复用关卡或诊断展示面）
    │   └── ReviewCase（本功能检查步骤与必需证据）
    └── Run / Review（特定版本、环境和人员的运行与核验记录）
```

“每项功能”指可独立说明目的、前提、操作和预期结果的用户/开发者能力，不按函数数量机械拆分。功能来源必须交叉检查现行规范、真实 Public 接口、配置/定义、调用链和已有测试；README 标题与测试宏数量不能单独作为功能已实现的证明。

每个插件记录功能审计状态；未完成审计时显示“功能范围待审计”，不显示“100% 覆盖”。每项已确认功能必须有案例或有责任、原因和审核记录的“不适用”说明。资源缺失、尚未接线与未实现不是“不适用”。

### 4.2 作者源与运行定义

实施时增量升级现有 `PluginDemoManifest.json` 的版本化结构，作为演示编目的唯一人工维护源；本轮保留其 v1 历史快照，不伪造功能明细。下一版本明确区分插件扫描结果、功能作者记录和场景记录，并保留旧版本来源。UE 运行定义由该源通过引擎工具生成，作为可校验派生物，经 GamePlatformData 加载；不允许 JSON 与 DataAsset 各自维护不同的功能规则。

真实 `.uplugin` 和内容登记表决定插件身份；AssetRegistry 与实际加载决定资产有效性；运行报告决定运行事实；人工报告决定签收。编目只建立映射，不取代上述真源，也不在 Widget 中读取任意外部路径。

### 4.3 必需字段

以下是待实现的数据合同，不是已经存在的反射字段；JSON 保持现有小写下划线惯例，C++ 按 UE 命名规则映射。

| 记录 | 必需内容与语义 |
| --- | --- |
| 插件 | `plugin_id`、真实描述路径、三层归属、代码/内容类型、功能审计状态；是否启用从当前目标读取 |
| 功能 | `feature_id`、所属插件、中文名称/目的、实现依据、实现状态、责任位置、案例关系；编号不依赖显示名称或地图 |
| 案例 | `scenario_id`、中文标题、主功能、关联功能、模板、运行方式、必需依赖、预检条件、地图/Widget/定义软引用、操作/复位能力、超时、检查用例 |
| 参数 | 参数身份、类型、单位、范围、默认值来源、是否可写、应用时机；禁止随意脚本或控制台字符串作为用户参数 |
| 运行 | `run_id`、案例和功能、请求代次、源码/构建/内容版本、目标/平台/引擎/设备、起止时间、真实终态、错误、清理结果、证据索引 |
| 人工核验 | 用例版本、关联运行、审核者、显式确认、通过/失败/阻塞、说明、逐项证据、签收时间与被替代记录 |

同一地图可以绑定多个 `scenario_id`；每个案例有独立准备、参数与清理。跨插件案例有一个主所有者，关联插件各自映射独立检查用例；不得因主案例通过就自动签收所有关联功能。重复身份、缺依赖、歧义映射和非法参数必须拒绝激活，并在菜单保留具体错误。

## 5. 状态模型与完成口径

| 维度 | 状态设计 | 不允许的推断 |
| --- | --- | --- |
| 功能实现 | 待审计、未实现、部分实现、已实现 | 文档有描述不等于代码已实现 |
| 演示接入 | 未登记、已登记待接线、资源/依赖阻塞、已接线待运行、可启动 | 文件存在或 `OpenLevel` 已受理不等于运行成功 |
| 本次运行 | 空闲、预检、准备、运行、停止清理、已完成、失败、取消 | 取消不是成功；清理失败不能仍显示正常完成 |
| 人工核验 | 未核验、核验中、通过、失败、阻塞；另有历史/版本过期标记 | 自动测试通过不能代签人工通过 |

进入请求返回的成功只表示受理；必须等待目标世界就绪、案例准备和依赖加载完成后才进入“运行”。UI 分别展示四维状态；默认显示缺口，筛选不能修改底层统计。

功能覆盖与案例覆盖分开：一个功能有多个异常案例，不能只运行正常分支就将其所有门禁判定通过。已审计功能数、已接线功能数、当前版本已运行数、当前版本人工签收数和未审计插件数分别统计；分母来自真实审计登记，分母未知时不显示完成百分比。

## 6. 演示中心 UI 规格

### 6.1 页面结构

| 区域 | 内容与行为 |
| --- | --- |
| 顶部 | SSLM 标题、当前目标与环境、源码/内容版本、搜索、层级/类别/状态/运行方式筛选、刷新；不硬编码插件数量 |
| 左栏 | 每个插件独立条目；平台、MOBA、项目分组；内容包为项目内部类别；禁用插件仍可查看信息 |
| 中栏 | 当前插件功能及案例列表，中文名称、四维状态、关联案例数、缺口摘要；技术探针与正式演示分组 |
| 右栏 | 功能目的、实现依据、前置条件、所需服务、操作步骤、预期结果、实际证据、进入/查看缺口/查看报告 |
| 场景覆盖层 | 插件与案例面包屑、功能切换、参数区、真实场景、执行/停止/复位/返回、事件与核验抽屉 |

空列表必须区分搜索无结果、插件未启用、未完成审计、未登记案例和资产缺失。无法启动的案例可查看详情与整改原因，不能用空按钮掩盖缺口。中文说明与英文稳定身份同时可检索。

### 6.2 交互合同

- 鼠标悬停/键盘焦点展示相同说明；Tab/方向键按视觉顺序导航，Enter/Space 激活。关闭详情恢复原功能条目的焦点，刷新保持仍有效的选中身份。
- Esc 优先关闭弹窗或抽屉；运行中请求返回先完成取消/停止与清理。结果以事件反馈，不吞掉切图失败。遇到超时可结束本案例并保留失败记录，不无限等待。
- 只有案例声明且真实支持的执行、暂停、停止、重置操作才显示为可执行。重置恢复本案例实际拥有的初始状态，不清空其他世界、玩家或内容包资源。
- 参数先校验、再显式应用；业务数值显示区与待提交输入区分开。重复提交采用请求身份和忙碌门禁；失败显示错误而非改成成功提示。
- UI 仅投影只读状态和发送受控命令。插件扫描仅初始化/显式刷新，动态场景数据通过事件；列表按需生成，不为每帧刷新重复扫描资产或重建全部条目。
- 帧率/耗时等诊断采样只在检查面板启用时进行，使用有界可配置采样；不得因此引入登录、会话、背包等业务状态 Tick。

### 6.3 视觉与资源合同

沿用自然、藤蔓、叶片、温润碧玉和连续柔和高光，内容区清爽，状态同时使用图标和文字；不能仅靠红绿区分通过与失败。文字和输入采用既有主题固定尺寸，窄视口通过折叠侧栏、滚动和安全区适配，不缩放整页字体。

目标检查视口包含 1920×1080、2560×1440、3840×2160，并检查较小可用区域和系统缩放；这些是待核验场景，不是本轮实测结论。减少动态效果时关闭装饰动画，业务状态仍完整可读。

所有 Widget Blueprint、布局、主题、样式、动画及其编译/保存/重载均通过正确正式工程上的 Monolith。新增 UI 归 `DBAUIPack_Core` 的开发专用范围；原 `/Game/Development/PluginDemos/UI` 资产按第 11 节迁移合同处理。本轮不创建任何二进制资源。

保留原稿 RGB、正确 sRGB 和白色乘色；独立 Alpha 保持线性。禁止 Monolith 0.23.0 的 `capture_scene_preview` 的 `widget` 路径。颜色验收采用原生客户端截图或规定的线性 RHI 回读与单次编码链路，新导入资源必须重做当前指纹下的真实审计。

## 9. 案例生命周期、资源与权威

1. 选择案例后进行身份、目标、插件、资产和测试服务预检；缺任一必需项时停在可解释的阻塞状态。
2. 进入前生成本次运行身份与递增代次，捕获本案例拥有的可恢复状态，按需申请 Data 租约。地图加载与功能准备分别确认，失败时撤销本次需求。
3. 同一实验世界默认只激活一个可修改状态的案例。明确的组合案例可以协调多个子案例，但必须声明每个子对象和句柄的所有权，禁止各自同时复位共享对象。
4. 操作只调用被演示插件的正式公开能力；必要开发夹具标注用途和端侧，不提供生产权威捷径。网络案例使用隔离测试服务与既有服务器目标；演示客户端不直接写服务器私有状态。
5. 完成/失败/取消均先停止接收新操作，再停止实例、取消异步、解绑委托、释放本次租约、恢复可恢复状态。世界已失效时只清理本地所有权，不访问旧 Actor。
6. 异步完成需复核世界、运行身份、请求代次和取消状态；每次请求只完成一次。迟到事件不得复活已退出 UI、覆盖另一案例或释放另一世界仍使用的资源。
7. 停止或切图发生超时时记录清理失败与残留范围；不自动杀进程、不清理整个项目缓存、不卸载其他调用方资源。无有效回退世界时显示可诊断错误，不盲用旧旅行地址。

案例中的服务器权威内容继续归 GameMode/服务器策略、GAS 和复制对象。视觉投射物、护盾、传送门演示不能替代权威实体与准入。单机真实调用、显式测试夹具、真实联网和编辑器制作四类运行方式必须在界面持续可见。

服务型案例的“复位”不等于回滚已提交业务事务：背包、订单和经济记录不得通过直接覆盖状态或删除流水恢复初始值。使用可销毁的隔离测试数据，或调用业务已有的受控补偿命令；没有合法复位能力时明确提示并结束当前案例，不提供伪复位按钮。改变持久设置或本地存档的案例也必须限定测试配置与隔离路径，不能影响用户正式配置。

## 10. 证据、人工核验与安全

编辑器入口复用 `UGamePlatformReviewCase`、`UGamePlatformReviewReport` 和 `UGamePlatformReviewSubsystem`。开发客户端仅导出待审证据并展示观察记录，由编辑器导入核对并签收；不在客户端链接 Editor 类型，也不复制一个新的审核框架。

补齐既有人工审核门禁时至少核对：用例合同完整；运行确已完成；案例/功能/用例身份匹配；源码、实际构建和内容版本可追溯；每个 RequiredEvidence 均存在且满足对应检查；审核者与显式确认来自真实人工。失败和阻塞说明也应记录，不能自动替换为通过。

证据目录沿用平台 Review 规范的实际约定：`Game/Saved/GamePlatformValidation/<RunId>/Review/` 保存审核证据与报告；已有 `Saved/Validation/PluginDemos/` 的工具记录只保留诊断或索引，引用同一个 RunId，不维护互相矛盾的签收真源。两处均为运行输出，不写入 Source/Content。

签收记录采用追加修订，保留原结论和被替代关系。版本、环境或用例变化后，历史通过仍可查，但不得计入当前版本通过数。未构建的新源码与旧编辑器二进制必须分别记录，禁止把当前 Git HEAD 当成已加载模块版本。

人工结论和运行结果分离：审核者可以确认“预期拒绝路径表现正确”，但不能把一次真实执行失败改写为执行成功。失败案例的自动期望匹配记录与原始错误同时保存；人工通过仍需完成该用例要求的全部观察与证据。

性能记录设备、目标、画质、并发条件和实测 CPU/GPU/内存；没有项目批准阈值时只报告观测，不捏造“达标”。UI 图像遵守当前颜色门禁，自动截图不代替人工视觉签收。

认证/支付/钱包演示禁止生产凭据和真实充值、退款；存档使用案例隔离目录，不覆盖玩家数据；网络请求有明确沙箱端点和失败提示。导入证据与描述字段均视为数据，不执行其中的命令或任意路径，检查路径边界与脱敏要求。演示菜单不是通用进程启动器。
