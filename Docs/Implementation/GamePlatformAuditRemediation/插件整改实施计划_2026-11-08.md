# SSLM 插件整改实施计划

> 按下列任务实施和验收。审查基线为 `main/f80bb02f`，执行基线包含工作区已有的竞技场退场与排队落点改动。

**目标**　闭合竞技权威转场和结算，补齐跨端资产归属，并让构建门禁检查真实目标及最终包。

**架构**　平台层持有应用流、准入和会话机制，MOBA 层持有竞技结算，项目层装配竞技扩展和玩法资产。Go Match 持有报名及对局状态，服务器控制面负责票据与权威落点。每条路径复用既有执行器。

## 约束

- 保留已有未提交改动。协议变更从 Shared 真源生成绑定。资产用 UE5.8 和 Monolith 操作，先读引用和备份，再保存、重载和核对引用。
- 使用既定 Win64 Development 增量构建入口，参数为 `-NoSharedPCH -NoUBA -MaxParallelActions 8`，Editor 另用 `-UsePrecompiled -AdditionalPlugins DBAServer`。Cook、Stage、验证制品保留在工作区 `Saved` 内。
- 验证分为源码回归、UE 原生资产、目标构建、最终包和联机准入。若启动验证客户端，先核对实际 Village 与 MainArena 服务器的战斗构建和复制合同，并核对不限帧设置。

## 任务 1　迁移火球权威配置

- [ ] 查清 `DA_DBA_Fireball_Flight` 的原生入边及所有写入入口，记录速度、追踪和主资产身份。
- [ ] 用 Monolith 将原资产迁入 `/DBAGameplay/Abilities/ProjectileFlight`，重存真实引用者。将 `Tools/Unreal/Combat/ProjectileFlightProfiles.json` 和引用清单改为该唯一路径。
- [ ] 冷加载火球技能与新路径，验证同一配置的 1,200→1,800 cm/s、0.15 s 和持续追踪。开发双端最终包均应有该配置。对保留资产的包级硬引用验证闭包，允许显式可选导入及引擎元数据。

## 任务 2　收口竞技重连、退场和普通世界准入

- [ ] 在 `DivineBeastsApplicationFlowSubsystem` 的通用恢复和蓝图兼容入口接入可选竞技扩展，使用现有 Match 重连、退场及返程票据。复用同一个应用流和会话迁移执行器。
- [ ] 转场意图与应用流节点及登录代次一起受理。只有接受的请求可以提交目标和发出离场通知，拒绝或重入请求不覆盖意图。
- [ ] 在 Go 世界准入签发边界校验当前可信出场状态。对局中的会话走 Match 授权，首次进入和普通世界转场继续走原有入口。
- [ ] 回归普通登录、竞技中断线重连、同帧重复转场、对局中普通入口拒绝和赛后返回原新手村排队点。

## 任务 3　恢复暂时失败的竞技结算

- [ ] 区分后端请求校验、结算冲突和可恢复的存储／传输失败。让可恢复故障进入 `GamePlatformArenaServerCoordinator` 的结算重试。
- [ ] 由竞技世界持有一个提交序列。按原比赛 ID、EndRevision 和已冻结结果退避重放，通过幂等结果确认提交。世界撤销时清理在途工作。
- [ ] 验证暂时写入失败、提交后回执丢失、重试期间关服及终态确认后的排空，结果只提交一次。

## 任务 4　验证排队落点采集资格

- [ ] 复用 Match 的真实报名身份，在控制面写入前校验玩家、角色、会话、Village 实例和有效期。由服务器采样坐标。
- [ ] 验证伪造、异角色、已过期和已取消报名拒绝，合法重复保留首次安全位置。历史报名继续采用现有安全出生回退。

## 任务 5　隔离专服配置和表现载荷

- [ ] 按实际 DedicatedServer、VillageServer 和 VillageDevelopmentServer 配置层清除客户端类扫描与视口覆盖。
- [ ] 在 `ServerPresentationExclusions.json` 和实际包审计中覆盖客户端输入表及明确的编辑器工具。收紧植物插件装配前，核对保留资产依赖和村庄碰撞／导航。
- [ ] 验证两类专服启动配置、包体和日志，客户端回查原有输入配置及资源。

## 任务 6　验证真实无竞技装配

- [ ] 在既有构建入口新增无竞技验证装配，按同一开关一起处理竞技插件、地图和配置扫描。默认正式装配继续包含完整竞技模式。
- [ ] 使用真实 UBT 装配和产物核对可选插件依赖。验证无竞技配置保留普通世界入口及新手村资源。

## 任务 7　校正插件门禁

- [ ] 以活动工程树为扫描范围，排除 Saved、历史工作树和生成目录。按正式机制、登记内容和获批第三方编辑器工具分别统计。
- [ ] 按真实目标条件解释天气依赖，并用 UBT 回执验证端侧隔离。执行 `ValidateDesignBaseline.ps1`、插件依赖与模块图回归、质量门禁和包体反例。

## 集成交付

- [ ] 检查修改范围和现有竞技场改动，运行相关 Go、UE 和架构回归。
- [ ] 完成受影响目标增量构建，按实际产物核对最终双端 Cook/Stage 及包依赖。记录每项证据及验证边界。
