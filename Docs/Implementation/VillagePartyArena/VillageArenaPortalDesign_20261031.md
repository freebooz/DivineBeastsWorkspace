# SSLM 新手村竞技传送门与约战设计

状态：**用户已于2026-10-31批准完整方案，按阶段实施中。** 实际完成与验证以同目录执行记录为准。

用户要求：从新手村通过五个传送门、组队等方式进入竞技场对战；结合现有游戏与工程给出推荐方案，人工确认后实施。

## 推荐方案

在新手村设置一个竞技集结区，五个传送门分别对应1v1、2v2、3v3、4v4、5v5。传送门是同一竞技服务的场景入口，点击打开已选模式的统一面板；实际传送发生在全员确认、后端分配MainArena并签发本人准入之后。五种人数共用现有地图、服务器目标与运行链路，不为每个门常驻一个独立服务器。

面板提供两个入口：**快速匹配**和**好友约战**。快速匹配适合单人或不满编队伍，复用当前队列；好友约战适合双方已经约好对手，新增固定名单邀请，随后进入同一候选确认、分配、准入、战斗及返回流程。

借鉴《魔兽世界》通过活动面板单人/预组队进入竞技匹配的做法，保留低门槛与组队社交；借鉴《最终幻想XIV》决斗须指定对手且对方接受的交互，明确区分随机匹配与定向约战。这里借鉴交互原则，不照搬它们的职业、排位、奖励或战斗数值。参考：[暴雪竞技练习赛说明](https://news.blizzard.com/en-us/article/23901945/weekly-bonus-event-arena-skirmishes)、[FFXIV官方决斗交互说明](https://na.finalfantasyxiv.com/lodestone/topics/detail/3e346198c51cd42590ae680297f30908c0bd0c4d)（后者为历史补丁说明，仅用于说明明确接受邀请的设计来源）。

## 玩家体验

### 五个门

| 显示 | 既有模式身份 | 单队容量 | 快速匹配报名资格 |
| --- | --- | --- | --- |
| 单人决斗 1v1 | Arena.Mode.Duel1v1 | 1 | 无队伍玩家或单人队伍 |
| 双人协作 2v2 | Arena.Mode.Team2v2 | 2 | 单人或2人以内整队 |
| 三人对战 3v3 | Arena.Mode.Team3v3 | 3 | 单人或3人以内整队 |
| 四人对战 4v4 | Arena.Mode.Team4v4 | 4 | 单人或4人以内整队 |
| 五人团战 5v5 | Arena.Mode.Team5v5 | 5 | 单人或5人以内整队 |

门按浅弧排列在村庄广场侧面的非战斗区域，避开出生落点、湖泊、教学路径与植被。建议门间距6米，门楣清楚标出人数；同一模型、材质和交互机制，模式通过定义数据区分。具体坐标在批准后原生勘察地面、导航和可达性再定，不由概念图猜测坐标。沿用项目自然、玉石、流畅藤蔓的美术语言，表现克制，不制作五套高成本常驻粒子。

靠近后显示“点击/F 竞技场·3v3”等提示；走过或碰触不自动传送。点击与键盘共用现有Interaction路径。首次候选距离采用平台现有250厘米，最终按原生可达性检查校正；服务器验证距离、视线、目标代次及选项有效性。门允许多个玩家共享交互，不被单人占用或消耗。

### 快速匹配

1. 点击门，打开统一竞技面板并预选对应模式，显示本人英雄、队伍人数、队长及成员准备状态。
2. 单人可直接开始，无须先创建空队伍。组队时由队长开始，其余成员收到现有20秒准备；无需所有队员一起跑到传送门。
3. 进入按模式/区域划分的队列，已组队名单整体分配。不满队伍可与其他单人/小队补满，必须组成双方各N人的完整比赛；不拆队、不降成另一人数、不用假玩家补位。
4. 找到对手后，每名玩家分别在现有30秒内确认。队长不代确认，拒绝/超时依服务器终态取消本候选，不把其他玩家强制带走。
5. 全员确认后显示加载，后端分配短生命周期MainArena，逐人签票，复用现有Flow/Loading/Session进入真实服务器。

报名后可以关面板、继续在安全村庄活动；HUD保留队列状态和取消入口。关闭面板不等于退队列。重复点门显示已有准备/队列/候选，不重复报名；切换模式前必须收到旧队列取消成功。

队伍超过门对应容量时说明原因并建议合适模式，不自动踢人或拆组。非队长可浏览模式和发起组队邀请，整队报名由队长提交。等待时间没有真实统计时只显示已等待时长，不编造预计人数或时间。

### 好友约战

- 在同一面板切换“好友约战”，选择附近玩家、好友或输入公开玩家ID；服务端解析对方真实队伍及队长。1v1可双方无队伍；NvN需要两支各N人的完整队伍，不把一个10人普通队伍拆成两队。
- 发起者必须是本人队长或无队伍单人；对方队长收到拟议的60秒邀请，明确模式和双方名单。拒绝、忽略或名单变化使旧邀请失效。邀请不生成比赛、不发传送票。
- 对方接受后，后端原子冻结两支名单，生成指定双方的候选；**不进入随机搜索队列**，也不借助“两队同时排队”碰运气。
- 全体成员收到同一30秒候选确认，作为最终准备；约战没有随机排队阶段，不再额外叠加一轮20秒排队准备。全员确认后进入与快速匹配相同的分配和准入链。
- 约战默认为练习，不新增排位分、货币、奖励或消耗。取消/拒绝不计比赛胜负；战斗结果仍按现有权威结算记录。

### 场内与返回

保留当前500×500米场景、暗场照明及无辉光状态。双方仍使用中央出生槽，中心点相距46米，不放到500米场地两端。沿用当前单局歼灭、禁止死亡自动复活、10秒开赛及20分钟上限，不在本次入口改造中另改战斗规则。

赛后提供“返回新手村”和“再战一场”。返回由后端按原逻辑体验重新寻找有效Village实例和安全落点，不能直接使用旧IP或旧旅行票。再战需双方明确同意并生成新一轮身份，复用已存在的MainArena分配/清理规则；若本次无法在现有合同中可靠复用，则第一阶段先返回集结区重发邀请，不能假装原地直接续局已实现。

服务器不可用、内容不兼容、角色未就绪、转服在途、排队未知等情况，面板显示具体安全原因；玩家保留在当前有效世界，不以本地OpenLevel替代真实准入。

## 实现边界

- GamePlatformInteraction继续负责中立交互会话与服务器校验，不出现项目模式ID、生肖或匹配业务；GamePlatformOnline/数据/会话职责保持唯一。
- 村庄门的Definition、模型、碰撞与关卡摆放归DBAWorldPack_Village。共享门模型优先复用项目已有合法归属资源；不反向引用村庄到通用资源包。
- 项目世界对象只发布中立活动入口与定义身份；由DBAArena的客户端组合根处理模式预选与页面需求。不得让DBAWorlds或公共组队模块硬依赖DBAArena客户端。
- 项目模式、匹配适配与场内界面归DBAArena；公共队伍页面和用户通知继续归DBAClient/DBAUIPack_Core。所有新增/修改UMG字号固定10，状态更新依赖首次快照与通知，Widget不Tick轮询。
- 门、队伍活动按钮、竞技菜单共用一个打开/报名实现。面板预选只影响浏览；已准备、已报名或已形成候选时，以服务端锁定模式为准。
- 约战合同以Shared/Contracts真源增量定义，由锁定工具链生成绑定；后端在现有matchapi/matchmaking内增加邀请、双方名单版本、截止、幂等和原子预留，不另造匹配器或准入服务。固定约战与公共队列最终共用候选构造校验、确认、持久分配、签票、补偿及返回。
- 每个玩家同时仅占用一个有效约战/准备/队列/候选/比赛资格；对手忙碌、名单变化、队长变化、重复提交及重连换认证代次均由权威事务收敛。
- 所有真实UI/关卡/定义通过Monolith创建、编译、保存与重载。所有Cook/Stage及临时产物位于当前工程Saved内。启动客户端前执行真实Village/MainArena战斗版本一致性门禁，不锁帧，不使用HWebCodex。

## 批准后的实施与验收

1. **五门与统一面板**：读取村庄真实场地，定点摆放五个模式入口；接通点击/F、模式预选与已有组队按钮；原生保存重载，截图供人工确认位置/字号/氛围。
2. **快速匹配闭环**：复用并核对现有单排/组队准备、队列、逐人确认、迁移与安全返回；针对重复点门、非队长、超额、取消响应未知、跨模式重入做必要回归。
3. **固定对手约战**：增量合同、服务事务、UI邀请和候选接线；覆盖双方名单变更、忙碌、超时/拒绝、重复请求、分配或签票失败、迟到回调与清理；双方始终进入同一指定候选。
4. **真实双端验证**：只构建受影响目标，复用固定成功参数；新增资产执行对应Client/Server Cook与剥离。核对实际运行Village/MainArena版本后受控启动验证。两个真实会话完成1v1“点门→确认→入场→结算→返回”；2v2/3v3/4v4/5v5分别需要4/6/8/10个真实会话验证，不把静态或模拟人数报告为人工联机通过。

推荐一次批准完整方案，实施按上述顺序推进；若只批准五门+快速匹配，则暂不新增约战协议、邀请页面与固定名单流程。任何尚未执行的构建、Cook、多人和人工阶段单独记录。
