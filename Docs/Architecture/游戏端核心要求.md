# 《神兽联盟》游戏端核心要求

> 适用范围：UE5.8 游戏客户端（Client，客户端）与 Dedicated Server（专用服务器）。
> 本文是游戏端设计、开发、审查和验收的核心入口；详细插件规则以 `Game/Plugins/插件开发规范.md` 和根 `AGENTS.md` 为准。

## 一、总体原则

1. **插件式开发。** 主工程 `Game/DivineBeastsArena.uproject` 保持薄装配，实际能力优先由插件承载；禁止把可复用能力持续堆入主工程。
2. **面向多项目复用。** 依赖方向固定为 `DivineBeasts（项目层） → MobaCommon（MOBA通用层） → GamePlatform（游戏平台基础层）`；项目层可直接依赖平台层，禁止反向依赖。
3. **高内聚、低耦合。** 每个插件必须职责单一、边界清晰、无循环依赖，不访问其他模块 `Private（私有实现）`，不通过隐式资产、配置或蓝图引用形成横向强耦合。
4. **三层类型单向继承。** 对存在稳定同领域抽象的类型，优先建立 `GamePlatform（平台基类） → MobaCommon（MOBA扩展，可选） → DivineBeasts（项目派生）` 的单向继承链；纯数据差异使用Definition/DataAsset实例，运行时协作优先接口、组件和组合，禁止反向继承和项目字段污染平台基类。详细规则见[三层类继承与扩展规范](三层类继承与扩展规范.md)。
5. **插件边界必须可说明。** 每个插件必须明确“负责什么、不负责什么、输入、输出、依赖、端侧、生命周期、数据所有权、网络权威、资源所有权、失败与清理方式”。
6. **独立验证与人工审核。** 每个重要插件必须具备独立的 Demo/Test Map（演示/测试地图）、Example（示例）、Debug/Editor Tool（调试/编辑器工具）或 Automated Test（自动测试）之一，并提供可重复的 Manual Review（人工审核）入口；无需进入完整《神兽联盟》流程即可验证插件。
7. **单团队适度拆分。** 当前由一个团队开发，插件拆分依据职责、复用、端侧、生命周期、测试和发布边界，不按组织结构机械拆分；禁止为了“完整”批量创建空插件、空模块和重复框架。

当前目录落地为39个平台插件＋MOBA层的GamePlatformArena（合计40个GamePlatform身份），另保留MobaPresentation及5个DBA代码插件；真实内容插件另计N。DBAArena承接项目竞技三模块，公共项目插件不依赖竞技；内容包在第三层内部。实施及未验收项见[三层架构实施规划](游戏端插件三层架构实施规划.md)。

## 二、客户端与专用服务器

8. **服务器权威。** Dedicated Server 负责移动校验、碰撞、GAS技能、属性、命中、伤害、治疗、控制、权威投射物、区域规则、出生、比赛状态与胜负；客户端不得决定权威结果。
9. **客户端负责表现。** Client 负责 UI（用户界面）、VFX（视觉特效）、SFX（音效）、Camera（相机）、纯表现动画、本地输入和反馈；表现失败不得改变服务器权威结果。
10. **端侧严格隔离。** 客户端专有模块不得进入 Server 产物，服务器专有模块不得依赖客户端表现实现；Server Cook（服务器烘焙）剥离纯 UI、Niagara（粒子特效）、皮肤、客户端音效等无关资源，同时保留碰撞、导航、规则和必要权威数据。
11. **正式服务器仅三种角色。** `OpenWorld（常驻世界：登录大厅+主城+开放世界）`、`Village（新手村+教学+训练）`、`MainArena（主竞技场）`；Lobby（大厅）不是独立服务器，Tutorial/Training（教学/训练）不是独立服务器角色。
12. **统一竞技服务器。** `MainArena` 统一支持 1v1、2v2、3v3、4v4、5v5，通过 ArenaMode（竞技模式定义）数据驱动；不得为不同人数建立五套服务器程序。单人可匹配，已有 Party（队伍）不可被拆散。

## 三、玩法、内容与表现

13. **GAS优先。** 技能、属性、效果、状态和冷却统一优先使用 Gameplay Ability System（GAS，游戏能力系统），不得再建立平行的技能/Buff/属性框架。
14. **数据驱动。** 英雄、技能、竞技模式、世界、VFX、SFX、动画、皮肤等优先由 Definition（定义）、Gameplay Tags（玩法标签）、Data Asset（数据资产）、Primary Asset（主资产）、Soft Reference（软引用）和 Content Pack（内容包）表达。
15. **表现与玩法解耦。** 玩法层产生权威事实或中立表现请求，不直接依赖 Niagara、具体 UI 或声音；`GamePlatformVFX（平台视觉特效插件）` 等平台插件只提供机制，项目差异通过内容和映射扩展。
16. **统一资源管理。** 主资产身份、加载、版本与租约统一归 `GamePlatformData（平台数据插件）`；各插件不得自行再造 Asset Manager（资产管理器）。
17. **真实资产。** `.uasset（虚幻资产）` 和 `.umap（虚幻地图）` 必须由 Unreal Engine（虚幻引擎）真实生成，禁止文本占位或改扩展名伪造完成。

## 四、工程与验收

18. **增量修改。** 所有开发基于现有工程原位修改；先检查真实目录、Git状态、已有实现和依赖，不重建同名模块、不复制第二套插件、不覆盖未提交修改。
19. **性能与生命周期前置。** 优先事件驱动、减少 Tick（逐帧更新）、使用异步加载、软引用、资源池和明确的世界/对象清理；性能结论必须有实际测量依据。
20. **共享契约唯一真源。** UE 与 Go 跨语言契约统一来自 `Shared/Contracts/GamePlatform` 和 `Shared/Contracts/Games/DivineBeasts`，禁止客户端、服务器、后端各自维护第二套协议。
21. **真实验收。** “完成”必须有真实代码、真实 Client/Server 构建、Cook（烘焙）、联机、世界切换、竞技、异常/取消、资源清理及必要人工审核证据；编译通过、文档完整或文件存在均不能替代运行验收。

## 五、插件验收最小标准

每个重要插件至少必须满足以下五问：

- 能否独立启用、编译和测试？
- 能否脱离完整《神兽联盟》流程独立演示并人工审核？
- 能否在其他项目复用而不携带《神兽联盟》专属依赖？
- 删除或关闭该插件后，无关系统是否仍可正常工作？
- 客户端、服务器、编辑器、资源和网络权威边界是否清晰？

不能满足上述要求的插件，应先重新审查职责和边界，再继续扩展功能。
