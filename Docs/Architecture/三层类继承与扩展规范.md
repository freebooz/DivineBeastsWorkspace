# 《神兽联盟》三层类继承与扩展规范

> 适用范围：GamePlatform（游戏平台层）、MobaCommon（MOBA通用层）、DivineBeasts（神兽联盟项目层）。
> 本规范约束类型继承、公共基类、接口扩展和数据Definition（定义）继承；模块依赖仍以单向插件依赖为前提。

## 一、总原则

三层依赖与继承方向统一为：

```text
GamePlatform（平台通用基类）
        ↑
MobaCommon（MOBA通用扩展）
        ↑
DivineBeasts（项目最终扩展）
```

代码依赖方向表达为：

```text
DivineBeasts → MobaCommon → GamePlatform
DivineBeasts → GamePlatform
```

禁止：
- GamePlatform继承、引用或公开暴露MobaCommon/DivineBeasts类型。
- MobaCommon继承、引用或公开暴露DivineBeasts类型。
- 为了项目方便把生肖、项目地图、项目VFX、项目UI等字段塞回平台基类。
- 通过循环继承、双向接口、Private头文件或资产父类反向引用制造隐性反向依赖。

## 二、何时必须设计基类

当多个项目、多个玩法或多个具体类型共享以下任一稳定概念时，应优先在更低层建立基类、接口或公共Definition：
- 稳定身份、版本、校验、生命周期。
- 相同运行语义，但资产或参数不同。
- 相同数据结构，只在上层增加字段或约束。
- 相同客户端/服务器权威边界。
- 相同加载、缓存、租约、审核或调试机制。

典型领域包括：
- VFX（视觉特效）。
- SFX（音效）。
- Animation（动画）。
- Camera（相机）。
- Character/Hero（角色/英雄）。
- Ability（技能）。
- Combat（战斗）。
- World/Region（世界/区域）。
- ArenaMode（竞技模式）。
- UI Screen/ViewModel（页面/视图模型）。
- Quest（任务）。
- Equipment（装备）。

## 三、继承与组合的边界

稳定“是什么”的类型层次使用继承，例如Definition、Screen、ViewModel、WorldDefinition、HeroDefinition。

运行时“怎么协作”的能力优先使用：
- Interface（接口）。
- Component（组件）。
- Subsystem（子系统）。
- Provider（提供者）。
- Strategy（策略）。
- Composition（组合）。

禁止构造超过必要深度的Actor/Subsystem继承树。原则上推荐：
- 数据/Definition：允许平台 → MOBA → 项目三层继承。
- UI/ViewModel：允许平台 → 项目或平台 → MOBA → 项目继承。
- Actor/Component：优先“平台基类 + 组件”，项目差异优先配置和组件组合。
- Service/Subsystem：优先接口与Provider注入，不要求三层都派生一个Subsystem。

## 四、VFX标准继承模型

平台层只定义通用视觉行为与执行契约：

```text
UGamePlatformVFXDefinition
├── UGamePlatformVFXInstantDefinition
├── UGamePlatformVFXAttachedDefinition
├── UGamePlatformVFXProjectileDefinition
├── UGamePlatformVFXBeamDefinition
├── UGamePlatformVFXAreaDefinition
├── UGamePlatformVFXShieldDefinition
├── UGamePlatformVFXPortalDefinition
├── UGamePlatformVFXTrailDefinition
├── UGamePlatformVFXWorldDefinition
└── UGamePlatformVFXCompositeDefinition
```

平台行为类表达“如何播放”，不表达“火球术、冰霜箭、龙息”等项目语义。

对于跨MOBA项目真正共享的表现语义，可在MobaCommon增加中间Definition或Context扩展；没有共享字段时不要为了三层形式强行增加空子类。

DivineBeasts项目层只在确有新增结构/校验时派生，例如：

```text
UGamePlatformVFXProjectileDefinition
        ↑
UDivineBeastsMagicProjectileVFXDefinition
        ↑
具体DataAsset实例：冰霜箭、火球、雷电弹
```

如果“冰霜箭/火球/雷电弹”只是Niagara、颜色、速度、参数不同，则不再创建C++子类，直接创建同一Definition类型的数据资产实例。

由于C++只能单继承，项目层不要同时建立一条与平台Behavior（行为）基类竞争的`UDivineBeastsMagicVFXDefinition` UObject根链。若神兽联盟多类魔法共享项目字段，优先定义可组合的`FDivineBeastsMagicVFXMetadata（神兽联盟魔法VFX元数据）`，再由各真实行为派生类持有：

```text
UGamePlatformVFXProjectileDefinition
        ↑
UDivineBeastsMagicProjectileVFXDefinition
        + FDivineBeastsMagicVFXMetadata

UGamePlatformVFXBeamDefinition
        ↑
UDivineBeastsMagicBeamVFXDefinition
        + FDivineBeastsMagicVFXMetadata
```

Area／Shield同理。只有Projectile／Beam／Area／Shield确实需要新增项目结构或校验时才开放对应平台`final`；SpellSemanticId、HeroPresentationProfileId、ContentPackId等项目字段放入项目Metadata或派生类，禁止复制平台Niagara执行、池化、伸缩和生命周期逻辑。

## 五、其它领域推荐继承链

角色：
```text
UGamePlatformHeroDefinition
        ↑
UDivineBeastsHeroDefinition
        ↑
十二生肖具体Definition资产实例
```

世界：
```text
UGamePlatformWorldDefinition
        ↑
UDivineBeastsWorldDefinition
        ↑
OpenWorld/Village/MainArena具体Definition资产实例
```

竞技：
```text
UGamePlatformArenaModeDefinition
        ↑
UDivineBeastsArenaModeDefinition
        ↑
1v1/2v2/3v3/4v4/5v5具体Definition资产实例
```

UI：
```text
UGamePlatformUIScreen
        ↑
UDivineBeastsUIScreen
        ↑
项目具体页面
```

ViewModel：
```text
UGamePlatformViewModelBase
        ↑
UDivineBeastsUIViewModel
        ↑
具体页面ViewModel
```

Surface（环境表面材质）不建立机械的UObject三层继承链：
```text
GamePlatformSurface通用母材质／材质函数／MPC合同
        ↓ 参数化复用
DBAWorldPack_* 中的 MI_DBA_* 项目材质实例与项目纹理
```
`DBAWorlds`只负责项目世界定义／组合，不派生一套`DivineBeastsSurface`平台替身；项目差异优先通过Material Instance（材质实例）、Texture Object（纹理对象）和内容包表达。只有未来出现多个项目都需要的稳定表面数据结构／校验契约时，才评审新增公共Definition或接口。

任务、装备、动画、相机、音效等遵循相同规则：平台提供稳定基础抽象；项目只增加项目特有结构；纯数据差异使用资产实例，不为每个内容对象增加C++类。Surface则优先使用材质函数／母材质＋项目材质实例的组合扩展，不为每种雪、苔藓、湿润场景新增C++派生类。

## 六、禁止的反模式

- 每个技能一个C++ VFX类。
- 每个英雄一个Actor派生类。
- 每个地图一个C++ World类。
- 项目层为了调用方便修改平台基类加入项目字段。
- MobaCommon包含生肖、神兽联盟ContentPack、项目地图ID。
- GamePlatform基类依赖MobaCommon或DivineBeasts头文件。
- 通过Blueprint父类或DataAsset父类形成文档未声明的反向依赖。
- Service/Subsystem为了“看起来三层一致”机械建立三层继承树。
- 为项目雪山、桃林、湿岩等内容建立`DivineBeastsSurface`平行基础插件或把`MI_DBA_*`、项目纹理反向放入GamePlatformSurface。

## 七、工程门禁

GamePlatformDeveloperTools现已增加`GP.InheritanceBoundary（继承边界）`源码门禁，并由`Tests/Architecture/InheritanceBoundaryAudit.psm1`提供PowerShell镜像检查；至少检查：
- GamePlatform公开类型的父类/属性/函数签名不得出现MobaCommon或DivineBeasts类型。
- MobaCommon公开类型不得出现DivineBeasts类型。
- DivineBeasts允许继承GamePlatform或MobaCommon公开类型。
- Blueprint父类与DataAsset父类同样纳入扫描。
- 跨层基类必须来自Public公开接口，不得继承Private类型。
- 发现反向继承、循环依赖或项目字段污染平台基类时阻止合入。
- 当前源码门禁不解析二进制Blueprint／DataAsset资产；真实资产出现后必须以AssetRegistry/DataValidation补充父类与硬引用边界。

## 八、当前工程审查结论

当前已有正确示例：
- UDivineBeastsHeroDefinition → UGamePlatformHeroDefinition。
- UDivineBeastsWorldDefinition → UGamePlatformWorldDefinition。
- UDivineBeastsArenaModeDefinition → UGamePlatformArenaModeDefinition。
- UDivineBeastsUIScreen → UGamePlatformUIScreen。
- UDivineBeastsUIViewModel → UGamePlatformViewModelBase。

Definition根体系仍处于迁移阶段：Flow、InputProfile、AbilitySet、Experience/Pawn、PCG、World/Region已经使用`UGamePlatformDefinitionBase`；Hero、AI、Quest、Inventory、Equipment、Entitlement、Progression、UI、VFX、ArenaMode等仍有直接`UPrimaryDataAsset`基类。迁移必须逐类审计PrimaryAsset身份、字段版本和`RequiredDefinitions`兼容，不能机械改父类。P0详见[插件系统P0收敛审计](游戏端插件系统P0收敛审计.md)。

当前VFX存在一个需要后续调整的点：Projectile/Beam/Area等平台行为Definition目前多声明为final，适合纯数据实例化，但会阻止确有项目结构扩展时的派生。后续应逐类审查：
- 没有上层扩展需求的行为Definition可以继续final。
- 确有稳定项目扩展需求的行为Definition去除final，并增加明确扩展点和验证合同。
- 不得为了“允许继承”全部取消final；只有存在真实上层结构需求时开放继承。

## 九、所有通用功能优先复用公共组件基类（2026-10-25 补充）

本章适用于全部新增/修改的蓝图、C++、Definition（定义资产）、Widget（界面控件）、PCG（程序化内容）、VFX（视觉特效）、SFX（声音效果）以及工具扩展。目标是**一个真实的通用机制、多份项目配置和组合应用**，不是“每发现重复函数都新建一个UObject基类”。

### 9.1 新功能先做通用性归属审查

每项功能在设计或修改前必须记录：业务语义、拥有者、调用方、复用范围、生命周期、Authority（服务器权威）归属、状态更新方式、已存在公共基类/接口及可证实的消费者。按以下顺序选型：

1. **已有平台组件/基类可满足**：直接继承或调用它；优先扩展稳定中立合同，不新建项目平行执行器。可用通用组件示例为 `UGamePlatformComponentWidget`（界面组件基类）、`UGamePlatformSlotWidget`（通用槽位）、`UGamePlatformSlotBarWidget`（通用槽位栏）、`UGamePlatformViewModelBase`（事件驱动视图模型）。
2. **跨游戏拥有相同身份、状态、扩展钩子和生命周期**：在平台层建立/完善通用基类；只有确实有竞技中间语义时才增加 MobaCommon（通用竞技层），项目类在已存在平台类型上扩展。
3. **跨领域只共享某一能力而不是同一个“是什么”**：优先使用可组合接口、轻量策略和值类型；例如 `FGamePlatformUISnapshotScope`（界面来源快照校验契约），不能强制所有 Widget/ViewModel 进入同一账号继承链。
4. **区别仅为参数、纹理、材质、Niagara、声音、角色、地图或主题**：使用 DataAsset（数据资产）、Definition（定义）、材质实例、蓝图子资产或数据驱动配置，避免空壳C++类。
5. **尚未出现真实消费者，或提取会破坏现行序列化/资源身份**：保持原实现并登记复用候选；禁止预建空基类和没有接口的管理器。

每一个公共基类或组件应具备确定的职责、公开合同、最少一个真实业务消费者、独立自动化门禁、变更兼容方案；稳定域出现第二个消费者后优先从已有合同扩展而不是复制第二套机制。

### 9.2 各域已有公共能力与建议的落点

- **UI槽位、资源条与通用提示**：现有 `UGamePlatformComponentWidget` → `UGamePlatformSlotWidget`、`UGamePlatformSlotBarWidget`、`UGamePlatformResourceBarWidget`、`UGamePlatformStatusEffectTrayWidget` 等现成基类。项目技能栏/背包/快捷栏只提交中立状态与美术差异；本轮已在 `UGamePlatformSlotWidget` 提供通用状态比较和命名控件展示，`FDivineBeastsInventoryCellPresenter`（项目背包格适配器）及技能栏投影差异已实际复用。
- **UI事件与账号/世界快照**：复用 `UGamePlatformViewModelBase` 的 Revision（修订号）、PageGeneration（页面代次）与事件；订阅验权源信息以 `FGamePlatformUISnapshotScope` 统一判断旧来源/重复/倒退通知。项目层 `UDivineBeastsScopedDomainViewModelBase`（领域来源视图基类）仍维持合法既有继承身份；组队和战斗警告控件复用同一个无状态校验合同，不创建第二个子系统或轮询器。
- **技能/战斗/人物**：优先复用 `UGamePlatformAbilitySystemComponent`（通用技能系统组件）、`UGamePlatformAbilityCastComponent`（通用施法组件）、`UGamePlatformCombatComponent`（通用战斗组件）；项目英雄只提供特有的 Definition 与GAS（游戏技能系统）策略。授权、命中、成本、冷却由服务器/GAS处理，蓝图/Widget不得成为权威真源。
- **背包、装备与快捷栏**：真实数据与命令继续归 `UGamePlatformInventoryClientSubsystem`（平台背包客户端服务），内容定义沿用 `UGamePlatformInventoryItemDefinition`（物品定义），项目 UI 只做名称/纹理/提示转换；不创建第二套物品实例、分页真源或客户端库存存储。
- **世界、水体、PCG与交互**：复用 `UGamePlatformWorldDefinition`（世界定义）、`UGamePlatformRegionDefinition`（区域定义）、`UGamePlatformPCGProfileDefinition`（程序化生成资料）、`UGamePlatformWaterInteractorComponent`（涉水交互组件），项目层以已有 WorldPack（世界内容包）和参数资产组合，不为每个湖/瀑布/山体新建独立平台实现；碰撞与导航必须经过服务器或一致烘焙认证。
- **相机、声音、特效**：复用 `UGamePlatformCinematicCameraProfile`（电影摄像机配置）、`IGamePlatformSFXService`（音效公共服务接口）、`UGamePlatformSFXDefinition`（声音定义）及现有 GamePlatformVFX（平台特效执行链），项目差异通过音效/特效目录和 Profile（资料配置）表达，不复制播放器、Niagara 池、负载预算真源或全局资产租约。
- **UI响应式与输入**：项目 Widget 从平台交互/导航控件派生或组合，状态变更消费 ViewModel 事件。禁止 Tick（逐帧更新）或常驻 Timer/Ticker（定时轮询）查询登录、背包、技能、目标/团队位置；连续视觉动画改由材质或原生动画根据事件起止参数处理。

### 9.3 蓝图复杂度与复用的执行门禁

- 首先以 UE5.8 AssetRegistry（资产注册表）和 Monolith 读取**真实** Blueprint ParentClass（蓝图父类）、EventGraph（事件图）、函数、宏、组件与软/硬消费者，不能用文件大小或默认Tick节点推断复杂度。
- 单个 Actor/Widget 蓝图拥有多个独立领域流程时，将实体能力下沉到已存在的组件，数据差异用 Definition；长执行链拆成职责明确的函数；高复用且具有对象生命周期的行为优先公共组件基类；简单无状态计算使用函数/策略，不创建 UObject。
- 不跨角色/世界复用无代次的全局状态；保持每 LocalPlayer（本地玩家）、World（世界）与 UI 页面正确的订阅绑定/解绑、取消和旧回调拒绝。
- 不允许公共插件硬引用 DivineBeasts 内容包，不允许竞技逻辑进入公共非竞技登录；不因 Widget 路径存在而认为事件图或 Runtime（运行时）已验收。
- 项目层 C++/Widget 派生类更换父类、稳定资产ID、字段版本或蓝图对象路径，必须先检查真实引用并提供回退映射；不能用文本文件模拟 `.uasset` 或绕过 Monolith。
- 必须分别提供：静态继承边界、Client/Editor目标编译、原生蓝图编译/冷重载、PIE/联机、Cook分端隔离和人工签收。**模块级编译通过不等于整目标或运行成功。**

### 9.4 当前优化边界

已完成的一批仅包括公共槽位视觉等价判断/控件投影和来源快照校验能力的实现与项目消费者迁移；这不等于对所有蓝图完成真正的父类改造。项目中存在历史双份 `WBP_DBA_UI_AbilitySlot`（技能槽控件蓝图），需要 Monolith 真实父类/树/消费者/冷重载验证才能裁定合并；旧新手村路径重定向器和已有软路径必须保留直至资产迁移审核。

### 9.5 公共来源与版本策略的唯一复用入口（2026-10-26）

对通用客户端 UI（界面）快照统一遵守已有 `FGamePlatformUISnapshotScope`（平台来源修订策略）：有 GUID（全局唯一来源身份）的页面/组件调用 `CanAccept`，仅有 FName（稳定资源名）的地图/倒计时/列表/技能栏等调用 `CanAcceptNamedRevision`。不得在各 Widget（控件）内再复制新一套“来源身份 + 版本递增”判断。调用该接口**不代表已通过玩家鉴权**，具体可见性、容量、数值范围、旧输入兼容仍由领域消费方验证。

四类项目世界 HUD（界面抬头显示）位置由 `FDivineBeastsWorldHUDRoute`（项目世界HUD路由策略）统一决定，保持作者WidgetSwitcher（控件切换器）槽位0常驻世界、1新手村、2教学、3训练，竞技HUD依旧独立。此路由是项目层纯策略，不需要引入平台公共世界HUD的生肖特定经验编号，也不需要创建新的 UObject/Widget 管理器。

逻辑 `DefinitionId`（定义编号）到 `FPrimaryAssetId`（主资产编号）只通过 `UGamePlatformPrimaryDataAsset::BuildDefinitionAssetId`（平台数据公共身份转换）构建，由SFX（音频）、VFX（视觉特效）和项目资源目录预载复用。失败时清空旧输出，具体业务错误码仍由消费者解释。

代码静态门禁入口：`Tests/Architecture/ValidateSharedUIComponentReuse.ps1`（公共UI复用检查）与 `Tests/Architecture/ValidateSharedDefinitionIdReuse.ps1`（公共定义身份复用检查）。这些检查不证明 UE5.8 原生编译或真实蓝图父类、Graph（执行图）和资产身份安全性。

`Tests/Architecture/ReportAllBlueprintAssetsOffline.ps1`（全量离线类别盘点）与 `Tests/Architecture/ReportBlueprintOfflineDependencies.ps1`（离线引用盘点）只提供规划依据。**不能用离线索引为0的引用数或节点数判定资产未使用、可删除、已经模块化或符合性能目标**。真正蓝图资产修改只能在恢复合法Monolith服务后，完整执行父类/控件树/依赖检查、作者视觉审核、编译、保存和冷重载。
