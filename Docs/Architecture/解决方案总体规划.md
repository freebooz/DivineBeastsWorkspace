1. 来源、适用顺序与本次整合决定

本版由三类材料组成：来源直接采用是用户附件的VFX设计；既定约束沿用是本会话已经确定的工作空间、三角色服务器、三层复用、竞技五模块和Go业务边界；本次补充设计用于填补注册、上下文装配、异步生命周期和验证契约。后者不是附件原文已经给出的实现。

用户附件完整保存在来源原文，全文1547行。参考原文保留其原有命名和图示，不作为未经整合即可执行的目录创建指令。现行目录以本文件为准。

IN01｜根目录采用最新明确命名。 唯一根目录为 DivineBeastsWorkspace（神兽联盟工作空间）。只改变工作空间路径，不因此改变 DivineBeastsArena.uproject（主工程）、主模块名、资产挂载点、Go模块导入路径或已发布协议身份。实际本机目录迁移须单独核对脚本、外部工具和引用。

IN02｜MOBA玩法结构不被附件中的示意展开覆盖。 附件第3章把 MobaCore（MOBA核心示例）、MobaHero（英雄示例）、MobaAbility（技能示例）、MobaCombat（战斗示例）、MobaMatch（比赛示例）、MobaArena（竞技示例）展开成多个插件；此前定稿采用 GamePlatformArena（通用竞技插件）中的五个模块。此次按“整合VFX设计”处理：保持五模块，不创建上述六个示例玩法插件；明确新增 MobaPresentation（MOBA表现语义插件），只承载附件第5章的语义与适配。这是对旧规则“第二层仅一个插件”的限定扩展，不修改五个竞技模块身份。[U1：117—130、328—388]

IN04｜保留VFX机制和项目表现模块，区分模块与插件身份。 GamePlatformVFX只保留GamePlatformVFXClient与GamePlatformVFXEditor。DivineBeastsPresentationRuntime及DivineBeastsPresentationClient继续存在于DBAClient/Source，不另建DivineBeastsPresentation.uplugin。项目上下文、语义映射和内容注册协调在此实现，不合并平台VFX／SFX播放器，不删除真实特殊实现。[U1：460—523、1307—1331]

IN05｜公共VFX资源采用附件归属，避免双份。 新规划使用 DBAPresentationPack_Core（项目公共表现核心包）承载附件规定的公共VFX定义、目录和资源；不再新建旧候选 DBAVFXPack_Core（旧公共VFX包归属）。已有真实资产包先保留身份，按引用清单迁移或暂作别名，不能只改目录名。旧公共音效、动画和UI包继续各自拥有资源，不因名称“公共表现”就未经评审合成一个巨大包。[U1：529—578]

IN06｜解决附件“开放世界不依赖MOBA”与依赖图之间的张力。 附件第15章要求非MOBA世界绕过MOBA，第17章又画出项目表现直接依赖MOBA表现的示意。本次补充为：DBAClient内的项目公共表现模块不硬依赖 MobaPresentation（MOBA表现）；两者通过基础层中立请求／上下文扩展接口联接，由竞技专用组合根装配。运行时可以先MOBA语义适配、再项目上下文补充，但代码不因此形成MOBA反向导入项目，通用世界也不被迫启用竞技。[U1：923—962、1062—1102]

IN07｜保留机制、语义、内容三分工，同时补齐实际解析顺序。 附件图示有的先写Definition再写Data，有的末尾把Definition和Catalog并列；本版统一为：先由目录解析得到定义主资产ID，再由数据服务加载定义，然后读其软引用加载实际资产。目录已经预加载定义时可命中缓存，但不得另造一套VFX资产加载器。[U1：867—918、1140—1183]

IN08｜补齐目录完全排序与冲突结果。 附件给出四种来源优先级及匹配维度，未规定完整排序键。本版在插件规范P13中规定资格过滤、精确语义优先、同语义级别内容包优先、具体度和显式优先级，并给出同键冲突及父语义回退规则。这是本次新设计，不是UE内建解析算法。[U1：966—1040]

IN09｜完整保留10种行为与17类内容分类。 行为仍是平台运行抽象，内容分类仍是制作与核验标签，二者正交；不创建17个插件、17套运行类或10种Actor。专项客户端定义类按附件保留，实际实现可以共享组件和执行器，不制造平行引擎。[U1：732—863、1382—1485]

IN10｜只推广可复用的工程约束，不臆造其他领域细则。 SFX（音效）、UI（用户界面）、纯表现动画和相机沿用语义入口、作用域服务、数据加载、内容所有权和验证思想；它们自己的行为分类、参数结构和性能预算不能照抄VFX十类型，须由领域设计定义。权威动作继续走动作执行链，而非可丢弃的特效请求链。

IN13｜2026-09-28用户界面生产策略。 《神兽联盟》项目自有 Widget Blueprint（控件蓝图）、RootLayout（根布局）、样式和界面动画必须通过 Monolith MCP 在正确的 Unreal Editor 工程上下文中创建、修改、编译、保存和回读核验；不得写文本占位或绕过引擎伪造资源。GamePlatformUI 只提供跨游戏机制，DBAClient 只提供项目 C++ 页面基类、ViewModel（视图模型）、路由和事件适配，公共界面资产归已登记的第三层内容插件 DBAUIPack_Core。界面由状态／命令完成／输入变化事件驱动，禁止业务 Tick、直接 HTTP 和客户端权威判定；密码只作为一次认证命令的瞬态输入。每次资产交付须记录 Monolith 操作、父类、控件契约、编译／保存／重载结果和未执行的运行验收。

2. 产品、技术与服务器基线

游戏采用 UE5.8（虚幻引擎5.8）C++；实时权威由 Dedicated Server（专用服务器）承载；长期业务由 Go（Go语言）后端承载。引擎补丁、编译器、Go、协议生成器及依赖以真实仓库锁定文件为准，不在文档中自行指定“最新版本”，不为通过测试降低生产版本。

唯一正式游戏工程是 Game/DivineBeastsArena.uproject（神兽联盟主工程）。主工程保持薄装配；正式客户端、服务器、编辑器分别构建。保留 DivineBeastsArenaServer.Target.cs（三角色共用服务器构建目标），默认不增加三个角色目标，更不为每种竞技人数创建单独二进制程序。独立资源烘焙配置、部署配置和进程实例不等于额外Target（构建目标）。

正式服务器角色只有三种：

OpenWorld  # 常驻世界：登录大厅＋主城＋开放世界区域
Village    # 新手村：正常新手村＋教学＋训练
MainArena  # 短生命周期竞技实例：1v1、2v2、3v3、4v4、5v5

Lobby（大厅）可作为常驻世界的体验、界面和区域名称，但不能恢复为独立服务器角色、独立资源池、独立项目世界插件或独立世界包。Village.Main（主新手村）、Village.Tutorial（教学）、Village.Training（训练）是体验配置。常驻世界可以有多个区域、实例和分片，并不意味着所有玩家共用同一个进程。

竞技采用两支比赛队伍，单队人数为1至5，总人数分别为2、4、6、8、10。人数由 ArenaModeDefinition（竞技模式定义）读取，不从已有协议枚举值推算。Party（赛前组队）不可拆分，但不是所有玩家的必经步骤；MatchTeam（局内比赛队伍）与赛前组队分开建模。

沿用此前已取消的玩法约束：不得复活五大阵营、旧派系、旧五行克制／共鸣、旧王印等规则。MOBA队伍敌我关系和美术素材中的普通词汇不构成恢复旧系统，不能按字符串机械删除第三方代码。

3. 责任边界与三层复用

**基础层 GamePlatform（游戏平台基础层）**提供跨游戏机制：身份、数据、流程、在线通信、会话、世界、通用角色／技能／战斗、表现框架和服务器控制面。它不知道生肖、项目技能或项目地图。

**类型层 MobaCommon（MOBA通用层）**在通用机制上组织竞技模式、队伍、比赛、计分与胜负；新增的表现插件只说明MOBA发生了什么。它不实现第二套Niagara（粒子特效）播放器，也不知道任何生肖资源路径。

**项目层 DivineBeasts（神兽联盟项目层）**提供稳定项目身份、真实流程、必要规则扩展、项目上下文、默认映射和内容包。ContentPacks（内容包）是这一层内部的交付分类，不是第四架构层。

本文件所有依赖图中 A → B只表示“A依赖B”；业务流程图另行标注为执行顺序。允许项目依赖类型层／基础层，类型层依赖基础层；禁止反向依赖和同层循环。三层不机械映射成三层类继承或三个同名子系统。

运行所有权另行划分。 Go后端拥有账号、角色档案、权益、订单、账本、业务组队、匹配和全局实例分配；UE服务器拥有世界内移动、命中、碰撞、技能和比赛事实；客户端拥有输入、经设计的预测和表现。子系统是服务生命周期机制，不能代替网络复制状态和实体组件。

4. 应用流程与两条世界路径

以下为执行顺序，不是代码依赖链：

Boot（启动）→ Initialize（初始化）→ Login（登录）
  → LoadPlayerProfile（加载玩家资料）
  → CharacterEntry（创建新角色／选择已有角色）
  → ValidateSelection（后端校验角色、英雄资格和选择版本）
  → RequestWorldAssignment（请求世界分配与一次性准入票据）
  ├─ 常规入口：OpenWorld（常驻世界）的登录大厅／主城安全落点
  └─ 新手入口：Village（新手村）主体验／教学／训练 → 完成后进入常驻世界
  → WorldReady（客户端必要资源＋服务器准入＋世界就绪）
  → 移动、交互、探索、可选组队
  → 选择1v1～5v5模式 → 匹配 → MainArena（主竞技场）
  → 权威比赛 → 幂等结果提交 → 结算显示
  → 后端重新确认返回实例／容量／版本／安全落点 → 返回常驻世界

应用流程不亲自访问数据库、计算伤害、创建特效或操作具体控件；使用服务契约和项目节点。UI（用户界面）提供操作入口，后端决定角色与权益是否合法。创建一个持久角色档案、选择一个已有角色、取得英雄权益和对局选人是不同业务，不得共用一个模糊的“HeroId即可创建一切”接口。

组队和匹配状态可与玩家在常驻世界中活动并存，不应作为世界状态的互斥替代。同实例的大堂、主城、野外采用区域流送或世界内传送；跨实例、跨分片、新手村和竞技场则走真实迁移与准入。比赛结束或断线后不能直接信任旧地址或重用已消费票据。

5. 完整工作空间与插件目录

这是一份完整目标归属树，不是扫描所得的现有工程清单。所有插件按“一期必建／条件拆出／随内容交付／二期预留”区分。条件拆出不意味着功能延期；只有形成独立职责、测试或发布边界才建立独立插件，不能批量生成空描述文件和伪可用接口。

分类文件夹不创建描述文件；真实插件拥有唯一同名 .uplugin（插件描述文件）。同一插件可有多个不同名模块。插件发现和模块组织由UE原生机制支持，但本项目三层分类是工程约定而不是引擎强制层级。[S01][S02]

6. MOBA竞技五模块与新表现插件的协作

竞技插件内五模块继续为 GamePlatformMobaCore（MOBA契约）、GamePlatformMobaData（MOBA数据）、GamePlatformArena（双端竞技）、GamePlatformArenaClient（竞技客户端）、GamePlatformArenaServer（竞技服务器）。

GamePlatformArenaClient（竞技客户端） → GamePlatformArena（双端竞技）
GamePlatformArenaServer（竞技服务器） → GamePlatformArena（双端竞技）
GamePlatformArena（双端竞技） → GamePlatformMobaData（MOBA数据）
GamePlatformMobaData（MOBA数据） → GamePlatformMobaCore（MOBA契约）
GamePlatformMobaData（MOBA数据） → GamePlatformData（平台数据）
GamePlatformMobaCore（MOBA契约） → GamePlatformCore（平台核心）

竞技运行可以使用通用玩法／战斗；数据不能反向依赖运行类型。通用英雄定义归平台角色，竞技参数经英雄ID关联；关闭MOBA仍能运行基础角色与常驻世界。

新增 MobaPresentation（MOBA表现语义插件）包含附件指定的两个模块。MobaPresentationRuntime（共享语义模块）只持有中立标签、上下文和事件，不持有资源；MobaPresentationClient（客户端适配模块）读取竞技已复制事实并产生中立表现请求。依赖是表现适配指向竞技事实，不是竞技权威规则指向表现插件。 竞技五模块不反向链接该插件，避免模块图看似无环、插件图却成环。

玩法事实的标签／载荷由原有事实拥有者定义，表现语义由表现模块定义，同一稳定标签只有一个声明所有者。必要双端表现语义模块可以由产品组合按目标启用，但服务器不因其可见而播放特效。也不能把C++局部委托广播当作网络传输。

7. 统一表现架构：VFX的正式整合

来源直接采用：基础层负责“怎么运行”，类型层负责“发生了什么”，项目层负责“最终显示成什么样”。[U1：5—46]

平台中立入口。 GamePlatformPresentationCore（表现核心模块）保留既有名称，定义轻量请求、结果、上下文扩展和服务契约；GamePlatformPresentationClient（表现协调模块）负责客户端作用域注册与调度。协调模块不反向导入具体VFX、SFX或UI播放器。真实播放器向中立扩展点注册，作用域关闭时撤销。

唯一VFX运行框架。 GamePlatformVFX（视觉特效插件）一期只含客户端和编辑器模块。客户端拥有服务接口、定义类型、目录类型、设置、私有世界子系统、提供者、解析器、执行器、实例登记、预加载协调、池化策略、质量策略、复合编排和诊断。V0.1.0 源码、中文说明、测试脚本和内容目录已接入 `Game/Plugins/GamePlatform/Presentation/GamePlatformVFX/`；它仍是生产纵向切片，当前只完成文件一致性核对，尚无 UE5.8 编译、Cook、Stage 或真实 `GamePlatformData`／`GamePlatformPresentation` 对接通过的证据。完整目录与验收要求见插件规范P08。[U1：161—322、1307—1331]

项目公共表现。 DBAClient中的项目表现模块提供项目身份上下文、默认目录及内容注册协调；不囤积大量英雄美术。它实现基础层中立上下文扩展接口，竞技专用组合根将其与MOBA适配联接。常驻世界直接使用项目表现或中立表现，无须安装MOBA。

竞技表现执行顺序：

服务器权威技能／战斗／比赛事实
  → GameplayCue（GAS表现通知）或已复制事实／受控网络消息
  → 客户端有效性、可见性、时效与预测去重检查
  → MobaPresentationClient（MOBA语义适配）
  → 通过中立扩展接口补充项目上下文
  → GamePlatformPresentationClient（客户端表现协调）
  → GamePlatformVFXPresentationProvider（VFX提供者）
  → GamePlatformVFXWorldSubsystem（私有世界级运行服务）
  → Catalog＋Resolver（目录与解析器）
  → Definition PrimaryAssetId（定义主资产ID）
  → GamePlatformData（数据服务）加载定义与所需资源
  → Niagara Executor（粒子执行器）
  → Instance Handle（可停止、更新和释放的实例句柄）

世界表现执行顺序：常驻世界／新手村事实 → 项目上下文扩展 → 中立表现服务 → VFX运行框架。以上箭头是调用／数据流；不表示MOBA插件依赖项目插件，也不表示项目公共表现必须导入MOBA。

低层 IGamePlatformVFXService（视觉特效服务接口）只给客户端集成、专门制作工具和测试使用；权威Gameplay（玩法）不能因接口“看起来很抽象”而链接VFX客户端模块。玩法正常入口仍是中立表现契约。

8. VFX行为、内容分类与资源归属

以下十种行为原样保留其含义，全部由唯一平台VFX框架实现：

01 Instant（瞬时型）
02 Attached（附着型）
03 Projectile（视觉投射型）
04 Beam（光束型）
05 Area（区域表现型）
06 Shield（护盾表现型）
07 Portal（传送门表现型）
08 Trail（拖尾型）
09 World（世界环境型）
10 Composite（复合型）

Projectile（视觉投射型）不是权威投射物；Shield（护盾表现型）不结算护盾数值；Area（区域表现型）不决定伤害范围；Portal（传送门表现型）不签发跨服票据。Composite（复合型）编排已有VFX定义，不另建第二套技能调度器。[U1：732—795]

以下十七类为内容制作／检索／任务／统计／人工核验分类，不对应插件或C++运行类：

01 Core（核心通用构件）
02 EnergyShield（能量、护盾与力场）
03 CastMagic（法术释放与魔法阵）
04 ProjectileBeam（投射物、光束与连接）
05 HitDamageExplosion（命中、伤害与爆炸）
06 AreaWarning（范围技能与地面预警）
07 StatusControl（持续伤害、状态与控制）
08 CharacterWeapon（角色、武器与动作增强）
09 Movement（移动、位移与穿行）
10 SummonTransform（召唤、变形、复活与死亡）
11 PortalSpacetime（传送门、裂隙与时空）
12 Environment（环境、天气、交互与破坏）
13 InteractionFeedback（战利品、目标与交互反馈）
14 UIScreen（用户界面、世界空间与屏幕空间）
15 UltimateComposite（终极技能与大型复合效果）
16 Experimental（高级模拟与实验）
17 Recovery（治疗、恢复、净化与复苏）

分类与行为正交：恢复类可以采用瞬时、附着、区域、光束或复合行为。保留原文 Core（核心通用构件）分类和 GamePlatformCore（平台核心插件）各自含义，不因名称相近混为同一模块。[U1：799—863]

内容所有权采用四类来源：平台中立默认、MOBA可选中立默认、项目默认、英雄／世界／皮肤内容包。它们是目录作用域，不是四层架构。基础层不存项目风格资源；公共VFX进入 DBAPresentationPack_Core（公共表现核心包）；专属效果归对应英雄或世界；皮肤包只覆盖表现，不写权威伤害和经济数据。

HeroId（英雄身份）、AbilityId（技能身份）、SkinId（皮肤身份）和 WorldContext（世界上下文）参与上下文匹配。它们必须来自合法上下文，不能靠用户提供任意路径突破权益、可见性或模块隔离。

9. 数据、目录、注册和租约

稳定语义使用 GameplayTag（玩法标签）；定义定位使用 PrimaryAssetId（主资产ID）；实际资源使用软引用。内容包身份、实例句柄、服务器ID与主资产ID不能混用。

GamePlatformData（平台数据）拥有统一发现、加载、版本、包依赖与调用者租约；VFX只分析自身需求并管理自己申请的租约，不自建全局加载器。[U1：1140—1183] 原生主资产和加载分组依托资产管理器；本项目目录及租约协议由工程实现，不是引擎自动附送的业务系统。[S05]

项目必需内容清单位于 Game/Content/Composition（项目组合资产），由流程组合节点／服务器任务装配入口选择；数据服务发现已安装已启用包，各领域服务注册目录并返回句柄。项目表现只协调表现部分，不能接管所有玩法内容的唯一管理权。

注册必须经过版本、目标用途、依赖无环和冲突预检；全部必需项成功后才发布本次解析视图。失败撤销本次已成功注册，释放本次租约，不遗留半启用状态。内容包无需为此增加C++模块；更不能把纯内容包的文件夹误当成自动注册动作。

解析的本版确定契约、退化规则和例子见规范P13。注销目录只停止未来选择，不得在现有表现实例仍使用资源时提前释放。实例、请求、预加载和注册句柄分别拥有职责；多世界共享加载需要由数据层合并所有仍有效租约。释放一个句柄不等于立刻完成垃圾回收或卸载全部资产。

10. 子系统、网络与权威动作

跨地图的流程、在线、会话、加载和数据门面按游戏实例生命周期管理；UI、输入和本地相机按本地玩家；世界、程序化生成协调和世界表现按当前世界。只在实际有服务职责时使用对应子系统，不能一插件一子系统。[S06]

VFX世界子系统放在客户端模块私有实现，选择可播放的客户端游戏世界；编辑器预览必须显式允许，烘焙命令行不得生成表现实例。全局静态单例、GWorld（全局世界指针）和固定第零号玩家不能替代作用域上下文。

服务器规则放游戏模式，公开复制状态放游戏状态／玩家状态，角色能力用组件，技能和属性使用GAS。游戏实例子系统／世界子系统不天然复制；网络事件必须指定复制通道、时效、重建和预测去重规则。持续护盾／光束状态不能仅依赖一次可能丢失的瞬时通知，新加入观察者需要从权威状态重建。

必要动作执行、取消、根运动或命中骨骼计算与纯表现动画分开。服务器可保留经审查确需的最小动作数据，但不因此加载纯VFX。低画质、特效缺失或迟到不能改变权威伤害；关键预警可选用低成本替代并标记诊断，不能把关键可读性预算简单降为零。

11. 模块目标与烘焙边界

共享模块可被客户端、服务器和编辑器消费；客户端模块仅在客户端／编辑器目标参与，服务器模块仅在服务器／编辑器目标参与；实际宿主类型、目标允许列表和加载阶段必须分别声明。ClientOnly（排除专用服务器的宿主）和 ServerOnly（排除专用客户端的宿主）的含义以引擎描述为准，名称不等同于完整目标隔离。[S03][S04]

VFX客户端模块必须允许编辑器读取其定义类型，所以不能用禁用所有Commandlet（命令行工具）的方式造成烘焙器无法反序列化源资产；同时，其世界服务必须在命令行和服务器世界不创建。服务器产品不链接VFX客户端模块，不加载纯表现目录、定义、Niagara资源或核验地图。编译、烘焙、Stage（暂存打包）、运行时加载分别审计，不以 Asset Bundle（资产加载分组）或目录名称当作剥离证据。

混合英雄包先保留单一源资产；按目标分别选择玩法／服务器／表现资产。无法安全剥离时再评审拆成同级玩法包和表现包，不能嵌套插件、复制权威定义或用文本占位UE资产。

原生Niagara池化和可伸缩能力优先使用；平台代码只负责策略映射和生命周期，不再实现按十类效果平行分裂的池。预算数值来自目标PC与移动设备实测，而不是把“GPU粒子”当作必然更快的结论。[S07]

12. 世界、PCG与地图制作

一期先完成常驻世界的真实三维入口、主城与最小野外活动区域，并同步接入服务器注册和准入。GamePlatformWorld（世界基础）拥有本实例上下文；全局分片分配仍在Go后端；GamePlatformPCG（程序化生成）消费世界上下文，不另存权威实例目录。

优先编辑器生成和审查后烘焙静态生态。客户端装饰性生成与影响碰撞、导航、采集、出生和胜负的结果分开；后者必须由权威执行或来自一致烘焙版本，不能只凭相同随机种子声称跨平台一致。

GamePlatformPCG 1.0 保留 `GamePlatformPCG（共享运行模块）+ GamePlatformPCGEditor（编辑器模块）` 双模块，不新增 ProjectPCG/DivineBeastsPCG 平行插件。平台层统一提供 Schema（属性协议）、P0～P9 Primitive（原语）、Definition（数据定义）、PriorityCarve（优先级挖洞）、基础放置器、WorldDirector（世界编排器）、Template Contract（模板合同）、Bake Manifest（烘焙清单）与 Editor Validator（编辑器校验器）；神兽联盟的具体 Graph Instance（图实例）、群系、作物、道路、围合和 MeshSet（网格集合）归 DBAWorldPack_* 世界内容包。M0/M1 先完成普通 Editor Static Generation（编辑器静态生成）闭环，HiGen（分层生成）/World Partition（世界分区）后置到 M2。

DBAWorldPack_OpenWorld（常驻世界包）包含地图源、世界／区域／体验定义、生成配置、数据层、环境资源与表现目录，大厅／主城／野外只是内部体验。新手村和主竞技场分别拥有对应包。外置Actor／对象编辑数据随地图完整提交，以引擎实际生成位置为准，不当作缓存清除。所有.uasset（资产）和.umap（地图）必须由引擎工具创建和迁移。

13. 共享协议与Go业务后端

跨UE与Go契约唯一真源在 Shared/Contracts（共享契约），分平台公共与项目扩展；后端内部服务／事件只在 Backend/internal/contracts（内部契约）。事件归属按真实消费者，不能一概把所有比赛或支付事件放到共享层。

C++生成源码位于 Shared/Generated/Cpp（C++生成目录），Go生成源码位于 Backend/generated（Go生成目录），分公共与项目输出但每种绑定只有一个来源。传输对象通过私有适配器转换，不进入公共玩法类型。需要C++绑定时先由统一构建编译外部库或采用已验证单一编译模块；只有头文件路径不代表实现已经链接。

保留五个Go薄应用入口：网关、身份、玩家数据、比赛、服务器控制。业务领域通过端口使用持久化、缓存和消息设施；领域不直接依赖第三方传输对象。后端当前公共平台／项目扩展内部布局以真实工程为准，此次插件文档不擅自重排Go结构。

预留 Commerce（交易）、Economy（经济账本）、Inventory（背包）、Entitlement（权益）、Progression（成长）和 LiveOps（运营）等职责。充值先确认可信渠道交易，再以幂等、可重试和可审计流程入账／发放；不能在角色资料直接加钱。已经落账的数据以冲正／补偿修正，不删除历史流水。可靠跨服务事件用事务发件箱和消费幂等，不宣称基础设施天然保证业务恰好一次。

比赛结果只接受绑定比赛的可信主竞技场服务器。一次性迁移票据绑定账号／角色、源或会话上下文、目标实例、版本、有效期和防重放身份；重连重新确认目标，不把旧大厅实例的票据换标签就复用。

14. 开发宿主、构建与两期交付

所有插件源码唯一位于Game/Plugins。当前只有一个正式.uproject与Client／Server／Editor三个Target，不创建DevHost或第二个正式工程。平台表现、通用世界、MOBA客户端／服务器分别使用同工程的测试配置与自动化入口验证，不复制源码。

非竞技装配显式禁用DBAArena、GamePlatformArena、MobaPresentation；竞技装配按端侧选择DBAArena及需要的MobaPresentation。DBAArena仅在Client／Editor目标依赖DBAClient，复用既有公开流程扩展，不建立第二个主流程执行器。当前.uproject仍是Foundation最小验证装配，不能把依赖闭包可解析写成产品主流程已启用或可运行。

第一期包含三个里程碑，而不是再拆多期。

一期A：锁定核心、数据、流程、在线、会话、加载、世界、输入、角色、UI、相机、服务器控制及最小PCG工作流；一名英雄、一个常驻世界白盒跑通登录／创建／选择／准入／真实三维活动。基础日志、配置、资格检查及验证同步具备。

一期B：完成通用技能／战斗、必要动作、平台表现、VFX客户端与编辑器、项目上下文和首批真实内容。先实现可验收的瞬时／附着最小纵向链，再按实际技能扩展到附件十行为；尚未支持的行为必须明确拒绝，不能用空类或统一“成功”蒙混。进入一期结束验收前，当前产品实际使用的行为全部实测；未用到的高级复合、特定护盾或环境策略按同一框架增量实现。

一期C：接入竞技五模块和MOBA表现两个模块，统一验证五种人数、组队不拆分、可信准入、权威胜负、结果重试、结算、返回世界与重连。需要的新手村教学／训练采用同角色不同体验。十二生肖全套美术不作为第一条闭环的前置。

第二期深化生态、AI、导航、任务、背包、权益、成长、装备、充值商城、赛季、皮肤和运营工具；扩展独立本地化、设置和遥测。对第一期框架只做真实需要的扩展，不重新创造播放器、加载器、竞技框架或世界目录。热下载和功能热激活另行设计，不把普通插件默认当作Game Feature（动态游戏功能）。
