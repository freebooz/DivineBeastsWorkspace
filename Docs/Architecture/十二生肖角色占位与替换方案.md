# 十二生肖角色占位与替换方案

## 1. 目标

十二生肖角色必须把“逻辑身份、权威玩法、客户端外观”分开。开发阶段使用 UE5.8 官方 Third Person Mannequin 的 Manny/Quinn 作为占位模型，并用十二套明显不同的纯色材质区分；正式美术到位后，只替换各生肖英雄内容包内的 Mesh、Material、Animation 等表现资源，不改变 HeroDefinitionId、后端协议、存档角色编号、外观 Profile ID 或内容包插件身份。

## 2. 三层归属

第一层 `GamePlatformCharacter（游戏平台角色）` 只负责跨游戏 Hero Definition、出生初始化契约、Definition Loader 和角色状态只读接口，不认识十二生肖，也不持有 Mesh/材质。

第二层 `MobaCommon（MOBA 通用层）` 不拥有生肖美术；竞技模块只消费稳定 HeroDefinitionId 和角色 Ready 事实。

第三层 `DivineBeasts（神兽联盟项目层）`：
- `DBAGameplay/DivineBeastsCharactersRuntime`：生肖身份、Server-safe Hero Definition、角色运行状态与项目初始化器。
- `DBAClient/DivineBeastsPresentationClient`：角色外观 Profile 类型、客户端软加载和表现适配。
- `DBAContentPack_Common`：Manny/Quinn 公共占位源与占位材质母版。
- `DBAHeroPack_Rat` 至 `DBAHeroPack_Boar`：每个生肖独立内容包；原型阶段放颜色材质实例和 Appearance Profile，正式阶段直接在原插件内替换真实角色资源。

## 3. 稳定身份

唯一协议真源为 `Shared/Contracts/Games/DivineBeasts/Schemas/hero-definition-id.schema.json`。十二生肖稳定编号为 `Hero.Zodiac.Rat` 等 12 个值。Go 后端与 UE C++ 绑定均由 `contractcodegen` 生成，禁止在客户端、服务器或 UI 再维护第二份 Hero ID 真源。

稳定外观逻辑 ID 采用 `Appearance.Hero.Zodiac.<Zodiac>.Default`；英雄内容包逻辑 ID 采用 `ContentPack.Hero.Zodiac.<Zodiac>`。真实角色替换时保持不变。

## 4. 原型视觉

公共源模型只保留 Manny/Quinn 两种，十二生肖交替使用。每个生肖拥有一个独立材质实例，颜色清单由 `Tools/Unreal/Characters/ZodiacPlaceholderCharacters.json` 管理。颜色只用于开发辨识，不进入服务器逻辑。

资产目标结构：

```text
DBAContentPack_Common/
└── Content/
    ├── Mannequins/                 # UE5.8模板Manny/Quinn及其必要依赖
    └── Materials/
        └── M_DBA_PrototypeCharacterColor

DBAHeroPack_Rat/
└── Content/
    └── Characters/
        ├── MI_Zodiac_Rat_Prototype
        └── DA_Appearance_Zodiac_Rat

...其余生肖同构
```

Hero Definition 位于 `DBAGameplay/Content/Definitions/DA_Hero_Zodiac_*`，只包含稳定 ID、移动/碰撞、版本、ContentPackId、AppearanceProfileId 等服务器安全数据，不引用 Mesh、材质、动画、VFX、SFX 或 UI。

## 5. 替换真实角色

真实生肖模型到位后，对单个 `DBAHeroPack_*` 执行以下替换即可：
1. 导入真实 SkeletalMesh、材质、纹理与项目专属动画资源。
2. 修改原 `DA_Appearance_Zodiac_*` 的软引用，指向真实资源。
3. 更新 Appearance Profile 的 `Version/ContentRevision`，关闭 `bDevelopmentPlaceholder`。
4. 如骨架改变，更新 `SkeletonCompatibilityId` 并由动画插件提供相应 Animation Profile。
5. 不修改 `Hero.Zodiac.*`、CharacterId、后端 API、角色创建/选择流程、GAS 能力身份或服务器规则。
6. 删除对应原型 Material Instance；当十二个角色全部完成后，再移除 `DBAContentPack_Common` 中不再引用的 Mannequin 原型资源。

## 6. 网络与版本

角色运行状态采用原子复制结构，包含 HeroDefinitionId、生肖、SpawnGeneration、AvatarGeneration、DefinitionVersion、ContentRevision。客户端只有在本地 Definition 版本与服务器认可版本完全一致后才进入 Ready。

`CharacterId` 继续 OwnerOnly 复制，不通过平台只读状态接口暴露。项目角色组件禁止 Tick，Definition 使用软加载并在身份/代次变化时取消旧租约。

## 7. Spawn 边界

`FDivineBeastsCharacterSpawnInitializer` 通过 `GamePlatform.CharacterInitializer` 模块化特性注册。它只初始化已经由平台统一 Spawn Operation 创建的 ACharacter，不自行 `SpawnActor`、不自行 `Possess`。

当前 `GamePlatformGameplay` 已有 Spawn/GameMode 契约，但统一 GameMode 实现仍需完成；在该平台层实现落地前，不允许项目层绕过平台边界自行建立第二套出生流程。

## 8. 开发回退

非 Shipping 构建在真实 `UDivineBeastsHeroDefinition` DataAsset 尚未生成时可使用瞬时逻辑回退 Definition，以便角色创建、共享 ID、网络状态和流程联调。该回退不含任何视觉资产。

Shipping 构建严格要求真实 Hero Definition 已注册到 AssetManager，缺失时角色不可创建，防止原型回退进入正式版本。
