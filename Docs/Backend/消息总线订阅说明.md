# 消息总线订阅说明

适用范围：`Backend/internal/platform/outbox` 与 `Backend/internal/platform/messaging/natsjs` 当前实现的跨服务集成事件发布链路。本文区分已实现行为、现有契约文件与尚未实现的订阅能力，避免把设计意图误称为生产可用消息消费者。

## 1. 当前实现结论

当前仓库**未实现具体订阅消费者**，也未包含 JetStream Stream、Consumer、保留策略、死信流或访问控制的创建配置。现有生产依赖适配器只实现以下发布链路：

```text
GameServerControlService.SubmitMatchResult
  → Match ResultService（以 MatchID 幂等保存）
  → 事务发件箱 Outbox（与比赛结果同一 PostgreSQL 事务）
  → Outbox Dispatcher（领取租约、发布、标记成功或失败）
  → NATS JetStream Publish(subject=Match.Completed, msgId=事件 ID)
```

本地 Compose 使用 `composition_local.go` 的日志发布器和内存仓储，不连接 NATS JetStream。因此本地启动成功只能证明 HTTP 路由与本地调用链可用，不能证明消息已发布或可被订阅。

## 2. 已发布主题

| 项目 | 当前值 | 说明 |
| --- | --- | --- |
| NATS Subject | `Match.Completed` | 当前代码唯一实际写入 Outbox 并由 JetStream 发布适配器映射的主题。 |
| 事件 ID | `match-completed:{matchId}` | Outbox `Message.ID`，同时传给 JetStream 的 `WithMsgID` 用于服务器端发布去重。 |
| 聚合 ID | `{matchId}` | Outbox 聚合关联标识。 |
| 发布者 | GameServerControlService 的比赛结果流程 | 只有与活动 MainArena Assignment 匹配的权威结果才能进入该流程。 |
| 负载编码 | UTF-8 JSON | 当前负载由 `Backend/internal/modules/match/result.go` 构造。 |
| 事件版本 | `eventVersion: 1` | 当前 JSON 负载中的业务版本。 |

当前负载示例：

```json
{
  "eventType": "Match.Completed",
  "eventVersion": 1,
  "matchId": "match-20260921-001",
  "arenaModeId": "Arena.Mode.Team5v5",
  "gameServerId": "mainarena-001",
  "winningTeamId": "team-blue",
  "endedAt": "2026-09-21T12:00:00Z"
}
```

`winningTeamId` 在当前 Go 实现中是字符串；平局时为空字符串。消费者不能根据客户端提交的数据重建或覆盖权威比赛结果。

## 3. 现有 Schema 与发布负载差异

共享契约中已有以下 Schema：

- `Shared/Contracts/GamePlatform/Events/Common/message-envelope.schema.json`
- `Shared/Contracts/GamePlatform/Events/Match/match-completed.schema.json`
- `Shared/Contracts/GamePlatform/Events/GameServer/game-server-unhealthy.schema.json`
- `Shared/Contracts/Games/DivineBeasts/Events/arena-match-completed.schema.json`

这些 Schema 描述的是含 `messageId`、`correlationId`、`traceId`、`producer`、`occurredAt` 和 `payload` 的标准消息信封，或项目扩展事件。**当前 `Match.Completed` 发布器尚未把上述完整信封写入 JetStream 数据负载**：它发布的是前一节的扁平结果摘要，并使用 JetStream `MsgID` 承载发布去重键。

因此，现阶段不能声称已实现“Schema 信封校验后的通用订阅”。任何新消费者在接入前必须明确选择：

1. 只按当前扁平 `Match.Completed` 负载消费，并把该消费者限制为过渡用途；或
2. 先完成发布器到标准信封的兼容迁移、版本策略和生产验证，再以 `match-completed.schema.json` 作为正式消费契约。

在两种方案确定前，禁止让消费者假定消息正文包含 `messageId`、`traceId` 或 `payload`。这是当前实现与共享事件 Schema 的已知边界，不是可省略的文档细节。

## 4. 订阅接入要求

新建 NATS JetStream 消费者必须由拥有基础设施权限的部署方案显式创建，且至少定义：主题匹配、Stream 名称、Durable Consumer 名称、投递策略、Ack 策略、最大重投次数、保留期、监控指标、失败告警和访问控制。仓库当前没有这些最终参数，本文不伪造数值或配置片段。

消费实现应遵循下列顺序：

1. 使用独立、稳定的 Durable Consumer 名称订阅 `Match.Completed`，不能用临时随机名称代替可恢复消费状态。
2. 收到消息后先做结构和版本校验；过渡期间按当前扁平负载校验，信封迁移完成后按共享 JSON Schema 校验。
3. 在本地数据库事务内记录消费幂等键和业务副作用，再发送 JetStream ACK。当前正文不含正式消息信封 ID 时，必须先完成幂等键来源评审，不能仅靠内存集合去重。
4. 业务副作用失败时不 ACK，使 JetStream 按部署配置重投；达到重投上限后应进入已审批的隔离/死信处理流程，不得静默丢弃。
5. 消费者对同一比赛结果的重复投递必须保持 idempotency（幂等）。`Match.Completed` 是结算后事件，重复发奖、重复写入排名或重复发送外部通知均不可接受。

## 5. 投递与失败语义

Outbox Dispatcher 按租约领取待发布记录。发布成功后才标记已发布；发布失败会增加尝试次数并回到待发布状态，后续轮询可再次尝试。进程重启、网络故障或“JetStream 已接收而本地标记尚未完成”的窗口都会导致至少一次投递语义。

`WithMsgID` 仅帮助 JetStream 在其去重窗口内抑制重复发布，不能替代消费者事务、幂等记录或业务唯一约束。消费者必须把重复消息视为正常情况，不能因为收到重复事件而重新结算或失败退出。

## 6. 其他事件状态

| 事件或 Schema | 当前状态 | 订阅说明 |
| --- | --- | --- |
| `Match.Completed` | 已有 Outbox 发布代码 | 可作为受控过渡主题接入，但必须处理第 3 节信封差异。 |
| `GameServer.Unhealthy` | 仅有 JSON Schema | 当前未发现实际发布代码、主题映射或消费者。 |
| `DivineBeasts.Arena.MatchCompleted` | 仅有项目 JSON Schema | 当前未发现实际发布代码、主题映射或消费者。 |

新增主题时必须同时增加唯一主题命名、发布所有者、完整 payload Schema、版本兼容规则、订阅说明、消费者幂等策略、失败处理和集成验证。不得通过扫描、加载顺序或默认订阅把未知主题自动接入。

## 7. 验证边界

当前可执行的验证包括 Go 中 Outbox 的幂等、租约与失败重试单元测试，以及 `Match.Completed` 与比赛结果同事务写入的单元测试。尚未执行或尚未实现的项目包括：真实 NATS JetStream 发布、Stream/Consumer 建立、跨服务 ACK、死信处理、消费者回放、生产权限和观测告警。它们不能标记为已通过。
