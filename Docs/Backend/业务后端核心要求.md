# 《神兽联盟》业务后端核心要求

> 适用范围：`Backend（Go业务后端）`、与 UE Dedicated Server（专用服务器）的业务控制面接口，以及 `Shared（共享契约）` 中由后端消费或实现的跨语言契约。
> 本文是业务后端设计、开发、审查和验收的核心入口；详细目录与实现以根 `AGENTS.md`、`Backend/DirectoryTree_CN_V1.1.0.md` 及现有接口/部署文档为准。

## 一、总体原则

1. **Go统一技术栈。** 业务后端统一使用 Go（Go语言）；实时移动、碰撞、技能、伤害、比赛过程等权威逻辑继续由 UE Dedicated Server（专用服务器）负责，后端不复制实时战斗引擎。
2. **领域模块化开发。** 业务能力按 Identity（身份）、PlayerData（玩家数据）、Party（组队）、Matchmaking（匹配）、Match（比赛）、GameServer（服务器控制）、ServerTransfer（跨服迁移）等明确领域组织；入口、领域、基础设施和传输层必须分离。
3. **面向多游戏复用。** GamePlatform（游戏平台公共能力）与 DivineBeasts（神兽联盟项目能力）分层；通用身份、玩家、匹配、服务器控制、支付/经济等能力不得硬编码生肖、具体地图或项目专属规则。
4. **高内聚、低耦合。** 每个领域模块必须明确职责、输入输出、数据所有权、事务边界、调用方向和失败语义；禁止跨领域直接访问对方数据库表、缓存内部结构或私有实现。
5. **五个薄入口保持稳定。** 统一保留 GatewayService（统一接入）、IdentityService（身份认证）、PlayerDataService（玩家数据）、MatchService（组队/匹配/比赛编排）、GameServerControlService（游戏服务器控制）五个入口；入口只负责装配、鉴权、编排和传输适配，不堆积领域规则。
6. **单团队适度拆分。** 当前由一个团队开发，优先保持单 Go Module（Go模块）和清晰领域边界；只有在独立扩缩容、故障隔离、数据所有权或发布边界明确时再拆新服务，禁止为了“微服务化”机械增加进程。

## 二、与游戏端的权威边界

7. **UE实时权威，Go业务权威。** UE Dedicated Server 决定实时比赛事实；Go 负责账号、会话、长期玩家数据、组队、匹配、世界/服务器分配、迁移票据、比赛结果持久化、经济与运营控制面。
8. **客户端不得提交权威结果。** 客户端不能直接写入余额、隐藏分、最终比赛结果、服务器状态或其他权威数据；关键结果必须来自可信后端流程或已绑定 Assignment（分配关系）的 Dedicated Server。
9. **服务器角色固定。** 后端服务器控制面只承认 `OpenWorld（常驻世界）`、`Village（新手村）`、`MainArena（主竞技场）` 三种正式角色；大厅属于 OpenWorld 体验，教学/训练属于 Village 体验。
10. **竞技统一支持1v1～5v5。** Match/Matchmaking 按 ArenaMode（竞技模式定义）支持 1v1、2v2、3v3、4v4、5v5；Party（队伍）是不可拆分的匹配原子，单人也可直接匹配。
11. **跨服迁移必须安全。** World Assignment（世界分配）、Arena Assignment（竞技分配）和 Transfer Ticket（迁移票据）必须有明确身份、目标、有效期、签名、一次性消费和防重放机制；比赛结束返回世界必须重新确认实例和安全落点。

## 三、契约、数据与一致性

12. **共享契约唯一真源。** UE 与 Go 的 OpenAPI、Proto、Schema、Event 唯一真源为 `Shared/Contracts/GamePlatform` 与 `Shared/Contracts/Games/DivineBeasts`；Go 内部协议仅放 `Backend/internal/contracts`。生成代码禁止手改或重复定义。
13. **领域数据有唯一所有者。** 身份、玩家长期数据、Party、匹配票据、比赛结果、服务器状态、钱包/账本等必须明确唯一写入所有者；其他模块通过接口或事件访问，不共享可随意写入的数据表。
14. **写请求必须工程化。** 所有关键写操作必须定义授权、校验、幂等、并发控制、超时、重试、事务和一致性边界，不能只实现“正常路径”。
15. **可靠事件采用 Transactional Outbox（事务发件箱）。** 数据库状态与需要发布的领域事件在同一事务中落库；消费者必须幂等。内存事件总线、内存仓储和日志发布器只能用于本地/测试，不能冒充生产可靠性方案。
16. **数据库变更必须 Migration（迁移）化。** PostgreSQL 结构变更只能通过版本化 Migration 管理；不得在生产启动时随意重建表、覆盖历史结构或删除业务流水。
17. **经济数据必须可审计。** 订单、支付、退款、钱包、背包/权益和账本形成闭环；金额使用明确币种的最小单位整数，不使用浮点；重复支付通知或发奖不得重复入账，纠错通过可审计事务完成。

## 四、基础设施、安全与运行

18. **领域与基础设施隔离。** PostgreSQL、Redis、NATS JetStream、Agones、HTTP/gRPC 等均通过 Adapter/Port（适配器/端口）接入；领域逻辑不得直接绑死具体中间件。
19. **生产依赖不得用内存替身代替。** 本地可使用内存仓储/模拟适配器，但生产必须明确接入真实数据库、缓存、消息和服务器编排，并通过生产 Composition（装配）门禁验证。
20. **安全默认拒绝。** 服务间接口、Dedicated Server 接口和管理接口必须鉴权；密钥、证书、Token、支付凭据不得进入源码、客户端或内容包；日志不得泄露敏感信息。
21. **可观测与运维标准化。** 每个入口统一提供 Live/Ready（存活/就绪）、Version（版本）、结构化日志、请求追踪和必要指标；超时、重试、积压、失败事件和依赖异常必须可定位。
22. **配置与环境分离。** 本地、测试、生产使用独立配置与 Secret（密钥）来源；代码不得硬编码个人路径、地址、账号或环境专属参数。

## 五、开发、验证与交付

23. **独立验证。** 每个核心领域和五个服务入口必须能够独立执行单元测试/集成测试；对外 HTTP/OpenAPI 或 gRPC 接口应提供可重复调用入口，Gateway 本地可通过 Swagger（接口文档）人工审核。
24. **真实自动化门禁。** 后端修改至少执行适用的 `go test ./...`、`go vet ./...`，条件允许时执行 `go test -race ./...`；同时覆盖协议生成新鲜度、架构依赖、数据库/缓存/消息集成和接口兼容性检查。
25. **增量修改。** 基于现有 Backend 原位修改，先检查真实源码、未提交修改、契约和迁移；禁止重建第二套后端、复制同名领域、随意重写协议或覆盖用户现有工作。
26. **不允许假实现。** 禁止空函数、固定成功、吞错、伪造返回值、测试内存实现冒充生产实现；失败、取消、超时、重试、并发冲突和依赖不可用必须有真实路径。
27. **文档与实现同步。** 服务职责、接口、协议、配置、目录、数据库 Migration、消息事件、部署和测试发生变化时，必须在同一变更中同步中文说明和验证记录。
28. **完成必须有真实证据。** 文件存在、代码生成、单元测试或本地健康检查均不等于生产就绪；关键功能必须通过真实依赖、跨服务调用、Dedicated Server 联调、故障/重试和部署回退验证。

## 六、后端验收最小标准

每个核心领域/服务至少必须满足以下五问：

- 数据和业务规则的唯一所有者是否明确？
- 是否可以独立测试，并且不依赖其他模块的私有实现？
- 是否可复用于其他游戏，而不携带《神兽联盟》专属逻辑？
- 写操作的授权、幂等、事务、重试和一致性边界是否完整？
- 本地替身、生产适配器、接口契约和实际部署证据是否能够清晰区分？

不能满足上述要求的模块，应先重新审查职责、数据所有权和边界，再继续扩展功能。
