## 一、建议结论

保留 **一个 ASC（Ability System Component，能力系统组件）＋领域化 AttributeSet（属性集）＋ GameplayEffect（玩法效果）修改与叠加＋ ExecutionCalculation（执行计算）做服务器结算＋客户端只读 ViewModel（视图模型）** 的结构，不创建第二套属性系统。

- `GamePlatformAbilitySystem（平台能力系统插件）`：仅有中立 `UGamePlatformAttributeSet（平台属性集基类）`、`UGamePlatformAbilitySystemComponent（平台 ASC）` 和 AbilitySet（能力集合）授予/撤销接口，**不定义生命、法力和生肖数值**。
- `GamePlatformCombat（平台战斗插件）`：持有已实现的四组领域属性集，分别为生命/护盾/元结算、攻击、防御、控制。其他项目可复用。
- `MobaCommon（MOBA 通用层）`：**当前不新增属性集**。记分板、胜负、复活倒计时、地图目标等更适合规则状态或 GameState（比赛状态），并非需要 GAS 属性聚合的数值。
- `DivineBeasts / DBAGameplay（项目玩法插件）`：持有 `UDivineBeastsMomentumAttributeSet（气势属性集）`；十二生肖差异走 HeroDefinition（英雄定义）、AbilitySet（能力集）、GameplayEffect 和执行策略，不复制同名攻击属性。
- `DBAClient（项目客户端）`：以 ASC 属性委托与受控状态快照产生生命条、护盾条、气势条、Buff/Debuff（增益/减益）和技能槽，不能在 UI 维护战斗属性的权威副本。

**基线统计：现有 5 个具体 AttributeSet 类、24 个字段，其中 22 个按 `COND_None + REPNOTIFY_Always（无条件复制并始终通知）`配置复制；`IncomingDamage` 和 `IncomingHealing` 为两个非复制元属性。中立父类没有定义数值字段。**

## 四、P0 第一优先：属性集创建、生命周期和复制

当前实际代码中，`UGamePlatformCombatComponent::BeginPlay（平台战斗组件启动）`在服务器对缺失的四类平台战斗属性集调用 `ASC->AddSet（向 ASC 注册属性集）`；`UDivineBeastsCharacterComponent::ApplyDefinition（应用英雄定义）`在服务器确认英雄资产后动态确保 `Momentum（气势）` 属性集。`ADivineBeastsGameplayCharacter（项目角色）`目前构造一个 ASC 和 Combat/Identity/Loadout 等组件，在 `BeginPlay/PossessedBy/OnRep_PlayerState（启动/附身/玩家状态复制回调）`绑定 Owner/Avatar（所有者/化身）。

**建议修改方向（需要先做最小联机验证后再实施）：**

1. 对所有可玩角色的固定核心属性，优先在角色构造期通过 `CreateDefaultSubobject（创建默认子对象）`部署四个通用战斗属性集与项目气势属性集；它们在客户端也具有可预测的类身份。游戏类型、NPC、一次性怪物可以根据明确的 PawnDefinition（角色类型定义）选择固定组合，不能强制所有非战斗实体拥有所有属性集。
2. 保留 ASC 作为角色上的唯一能力系统组件；如后续要把 ASC 迁移到 `PlayerState（玩家状态对象）`以跨死亡保留技能，必须作为独立的生命周期迁移评审，不应一边修属性一边改变Owner架构。
3. **避免构造期固定子对象和现有 `CombatComponent->AddSet` 二次创建**：先通过 `GetSet（取已注册属性集）`检验已存在，服务器与客户端都必须能解析正确对象；任一阶段缺少核心属性集应当 Fail Closed（拒绝进入玩法就绪），而非默认返回0继续战斗。
4. 可选插件属性集继续由 AbilitySet（能力集合）授权添加，但保持现有 `UntilASCShutdown（ASC关闭前存活）` 语义，不在撤销技能或换装备时立即删掉已有属性集对象，以免复制迟到、活动效果与 UI 委托悬空。
5. 只允许服务器下发可信的基础属性与技能授权；客户端只能监听 `OnRep + GAMEPLAYATTRIBUTE_REPNOTIFY（属性复制回调）` 和 `GetGameplayAttributeValueChangeDelegate（属性值变化事件）`，不能通过客户端 RPC（远程调用）写入战斗数值。
6. 用独立的 World/Spawn/Avatar Generation（世界/出生/化身代次）隔离换英雄、跨地图和重连事件；释放旧委托、旧技能/效果引用，不让旧角色异步 Definition（定义）覆盖新角色。

**关键验收：** Dedicated Server（专用服务器）+ 两个 Client（客户端），分别验证同一角色的五个属性集在服务器、拥有者及获准观察的远端都能获取正确实例；多人重连、角色切换、死亡重生不重复创建属性集也不丢失订阅。

## 五、P0 第二优先：正式属性初始化

推荐使用 **“英雄基础值定义 → 服务器属性初始化GE → 装备/等级等有效修正GE → 最终当前值”** 的顺序。

- `HeroDefinition（英雄定义）` 只存角色初始基础值/成长配置的权威版本，不复制第二套运行时属性。当前 Definition 只明确包含 `Momentum（气势定义）` 和 `DefaultAbilitySetId（默认技能集ID）`；生命/攻击/防御等完整基础数值配置表需要另行统一建模，而不是按生肖硬编码在 C++ 分支里。
- 可定义共享 `GE_InitializeCombat（战斗基础属性初始化玩法效果）`、`GE_InitializeMomentum（气势初始化玩法效果）`，由服务器在有完整 ASC、已验证 HeroDefinition、正确 AvatarGeneration 后应用。正式业务初始化建议尽量走 GAS base value（基础值）或 Instant GE（瞬时玩法效果）入口，谨慎保留 `InitHealth/InitMomentum（直接初始化属性）` 仅作为明确的构造/启动初始化用法。
- 启动时的 **基础属性、技能授权、启动效果** 必须有唯一版本与来源；HeroDefinition重载和断线恢复不得重复叠加 `Instant GameplayEffect（瞬时效果）`。执行同一版本初始化应幂等。
- 现有 `AbilitySet` 的属性条目用于“这个 ASC 拥有什么属性集类”，**不负责定义完整的英雄数值表**；基值资产、初始 GE、装备修正的来源分别建账。

### Base / Current（基础值/当前值）原则

GAS的 `FGameplayAttributeData（玩法属性数据）`同时保存 Base（基础值）和 Current（当前值），持续增减益可以临时改变 Current，退出效果后自动恢复。**不要直接把一个临时Buff反复写入Base，否则会造成叠加与移除错误。** Unreal Engine 5.8 官方属性文档明确了这个区别。见文末资料。

## 六、P0 第三优先：最大值联动与数值安全

当前 `PreAttributeChange（属性修改前回调）` 对生命、护盾、气势和失衡设置了初步Clamp（裁剪），`PostGameplayEffectExecute（玩法效果执行后回调）` 在对应属性集中处理部分收尾。这是正确起点，但不能将它直接视为“各种效果组合下已经无越界”。

建议按每类 Current/Max（当前值/最大值）对制定明确策略：

| 事件 | 建议策略 | 必须测试 |
| --- | --- | --- |
| `MaxHealth（最大生命）` 提升/降低 | 默认保持当前生命百分比，或保持绝对生命后Clamp；**必须在项目规则中选一种** | 升上限、降上限、装备卸下、Buff到期、接近死亡 |
| `MaxShield（最大护盾）` 改变 | 建议保持已获得护盾的绝对量并限制到新上限，除非技能明确提供额外盾 | 护盾溢出、护盾失效、真实伤害 |
| `MaxPoise（韧性上限）` 改变 | 依据控制设计选择比例或绝对值保持 | 连续破韧、死亡重生、减益到期 |
| `MaxMomentum（气势上限）` 改变 | 默认当前气势只Clamp，严禁把临时增上限当作气势实际增长 | 换英雄、气势消耗、上限回退 |
| 所有数值 | 拒绝 NaN（非数）、Inf（无穷）、负基础值、超大输入 | GE叠加、SetByCaller异常、客户端预测回滚 |

特别注意：`PreAttributeChange` 与 `PostGameplayEffectExecute` 触发时机不同，不能只依赖后者处理 Duration/Infinite（持续/无限期）玩法效果引发的属性上限变更。应覆盖Base与Current变化路径和属性聚合器回滚后的行为。

## 七、伤害与治疗执行：先完善链路，不增加重复属性

现有 `UGamePlatformDamageExecutionCalculation（伤害执行计算）` 已使用 `AttackPower（攻击强度）`、`AbilityPower（技能强度）`、暴击、穿透、护甲、魔抗和减伤，输出到 `IncomingDamage（待结算伤害）`；`CombatComponent（战斗组件）` 随后处理护盾、生命、死亡与战斗事件。`HealingExecution（治疗执行）` 输出到 `IncomingHealing（待结算治疗）`。这套链路应保留。

建议再做三项强化：

1. 将源与目标的计算依赖梳理为 `GameplayEffectAttributeCaptureDefinition（玩法效果属性捕获声明）`，在 ExecutionCalculation（执行计算）中按 Source/Target（施放者/目标）、Snapshot（施放快照）与 GameplayTag（玩法标签）约定取值。当前 C++ 从 ASC 直接 `GetSet<T>` 取现值可以算数值，但难以系统处理施法时快照、标签条件和复杂临时Buff叠加语义；迁移必须用伤害回归测试锁住旧公式输出。
2. 保持 `SetByCaller（调用者注入数值）` 的安全门禁：验证技能定义/身份、施放者资格、能否暴击及伤害类型，且 CritRoll（暴击掷值）必须与服务器已验证 EventId（事件ID）关联。客户端不得直接提交已确认的最终伤害或自行决定暴击命中。
3. 严格区分 `DamageReduction（减伤比例）`、`Armor/MagicResistance（护甲/魔抗）` 与 Shield（护盾）吸收；项目既有 TrueDamage（真实伤害）规则绕过护甲、魔抗和通用减伤。如改变“真实伤害是否绕过护盾”，必须另立明确规则，不可从属性集名称推断。

## 八、P1：让已有但未闭环的属性真正工作

| 属性 | 归属建议 | 推荐运行机制 | 验收 |
| --- | --- | --- | --- |
| `AttackSpeed（攻击速度倍率）` | 平台攻击属性集 | 定义为基础攻击间隔倍率；服务器技能/攻击调度消费，动画速率仅作同步表现。明确冷却与攻速是否相互作用 | 攻速0.5/1/2、攻速Buff叠加、攻击间隔、网络预测与服务器校正 |
| `Poise（失衡韧性）` / `PoiseRegen（韧性恢复）` | 平台控制属性集 | 由权威命中/技能事件扣韧；破韧结果触发可控GE/标签；脱战后服务器按明确周期恢复 | 连击破韧、免疫标签、上限与恢复、NPC批量性能 |
| `MomentumGainMultiplier（气势获取倍率）` | 项目气势属性集 | 命中/受伤/技能条件产生由服务器确认的气势Delta（变化量），在合规GE中乘倍率 | 重复事件幂等、连击、叠Buff、死亡重生 |
| `MomentumDecayRate（气势衰减速率）` | 项目气势属性集 | 由项目规则声明脱战/时间窗口；服务器集中调度周期GE，不允许客户端本地每帧减气势 | 断线/切世界、停止与恢复衰减、帧率无关、数值守恒 |

**优先不要再加攻击速度以外的“命中率、闪避、生命偷取、治疗强度”等整套字段**，除非正式战斗规则明确需要。需要时优先评估现有技能效果/标签/自定义计算策略是否足够；有稳定可叠加、可持续修改的数值语义才新增Attribute。

## 九、P2：可选资源与属性集扩展

**仅在真实角色原型需要独立资源时**添加：

| 候选AttributeSet（英文/中文） | 建议字段（英文/中文） | 准入条件 |
| --- | --- | --- |
| `UGamePlatformManaAttributeSet（通用法力属性集）` | `Mana（法力）`、`MaxMana（最大法力）`、`ManaRegen（法力恢复）` | 出现至少一种真实法力消耗技能与多英雄复用需求 |
| `UGamePlatformEnergyAttributeSet（通用能量属性集）` | `Energy（能量）`、`MaxEnergy（能量上限）`、`EnergyRegen（能量恢复）` | 与气势、法力明确不同且可跨项目复用 |
| `UGamePlatformStaminaAttributeSet（通用耐力属性集）` | `Stamina（耐力）`、`MaxStamina（耐力上限）`、`StaminaRegen（耐力恢复）` | 真实冲刺、翻滚、格挡等独立耗竭玩法 |
| `UGamePlatformMovementAttributeSet（移动属性集，暂不新建）` | `MoveSpeed（移动速度）` 等 | 仅当真实移动速度Buff/Debuff需要跨游戏GAS化，并已定义 CharacterMovement（角色移动组件）唯一速度适配端口 |

**当前不建议新增力量、敏捷、智力、幸运、物理/魔法命中、闪避、PVP专属伤害等属性。** 不同游戏定位和成长体系高度不同，过早塞入通用Combat会损失复用性。即使将来上线上述可选资源，也应每个数值语义有唯一真源、不复制项目Momentum（气势）。

## 十、Buff / Debuff（增减益）、控制和 UI 的正确映射

`GameplayEffect（玩法效果）` 负责Duration（持续时间）、Period（周期）、Stacking（叠层）、Modifiers（数值修正）与GameplayTag（状态标签）；`AttributeSet（属性集）` 只负责数值，例如生命与减伤。**不要为眩晕、沉默、灼烧、中毒、免疫各做一个布尔型AttributeSet字段**。

| 示例状态 | GAS层的权威承载 | 属性处理 | UI表示 |
| --- | --- | --- | --- |
| 攻击增强Buff（增益） | 持续GE（GameplayEffect） | 修改AttackPower或AbilityPower当前聚合值 | Buff图标、来源、叠层、剩余时间 |
| 护甲削弱Debuff（减益） | 持续GE | 临时修改Armor或DamageReduction | Debuff图标及可驱散标识 |
| 中毒DoT（持续伤害） | 周期GE、服务器结算 | 每周期走伤害Meta与Combat事件 | Debuff图标、剩余时间和战斗飘字 |
| 持续治疗HoT（周期治疗） | 周期GE | 每周期通过治疗结算入口 | Buff图标、治疗飘字 |
| Stun/Silence（眩晕/沉默） | GE赋予Control GameplayTag（控制标签） | Tenacity缩短实际持续时间 | 强控制独立提示及倒计时 |
| 免控/免伤 | GE赋予免疫机制标签/条件 | 抵抗由战斗授权与策略核实 | 免疫标识、文本，不只依赖颜色 |
| 攻速强化 | 持续GE | 修改AttackSpeed当前聚合值，实际调度器消费 | Buff图标与技能/攻击节奏显示 |

当前 `GamePlatformUI（平台UI）` 已有 `UGamePlatformStatusEffectTrayWidget（状态效果托盘）` 的分组、驱散标签、重要性与溢出机制；新建的具体Widget Blueprint（控件蓝图）是视觉资产，不能直接读取所有敌方GE。**Mixed（混合）复制模式下非拥有者并不获得所有活动效果详情**；竞技敌方/首领状态通过业务授权的只读StatusEffectSnapshot（效果快照）投影，必须遵守迷雾与观战权限。

## 十一、复制、预测与网络安全策略

- 当前 `UGamePlatformAbilitySystemComponent（平台 ASC）` 默认使用 `Mixed（混合效果复制模式）`；22个 AttributeSet 状态属性配置了 `COND_None（无条件属性复制）`。这不等于每个远端观察者应该看到全部数值，特别是竞技模式中的攻击、穿透、气势倍率和防御内部参数。
- **P0 不立即一键改成 `OwnerOnly（仅拥有者）`**：先做一份属性可见性矩阵，区分自己、队友、敌人、观察者、无视野敌人、Boss与普通NPC，并核实本地预测、服务器伤害计算、目标框是否依赖这些值。
- 成功复制的 `RepNotify（复制通知）` 应调用 `GAMEPLAYATTRIBUTE_REPNOTIFY（GAS属性复制宏）`；客户端 UI 委托必须在换Owner/Avatar、销毁和跨图时解绑。
- 对非拥有者只需要生命比例、是否硬控、重要Buff时，优先考虑已授权的定制快照，而不是广播所有精确隐私数值；频繁变动值按网络频率和精度预算制定单独的回归性能基线。
- 预测能力用于用户操作反馈，但伤害、击杀、物品持久资产、技能授权和真实数值修改仍由 Dedicated Server（专用服务器）定案。处理客户端预测失败和回滚，不要双次叠加 Instant GE。

## 十二、等级、装备、成长、存档的归属

- `GamePlatformProgression（平台成长）` 或 Go业务后端保持长期的等级、经验、解锁和持久角色资料**唯一真源**；不因为“角色有等级”就在GAS中必然新增 `LevelAttribute（等级属性）`。
- `GamePlatformEquipment（平台装备）` 保存装备资格与装备事实；装备对最终攻击/防御的影响，通过与装备实例绑定的授权GE应用到已有 AttributeSet；卸装备撤销该来源句柄。
- `GamePlatformSave（本地存档）` 不保存服务器权威当前生命、攻击力、气势、技能权限；需要重进世界恢复的事实由权威业务系统返回，再在服务器重构本次 ASC 的属性与效果。
- `GamePlatformInventory（平台背包客户端）` 仍消费后端权威库存，不把物品数量、货币余额或支付结果做成GAS属性。
- 项目十二生肖等级/皮肤/技能树差异优先表驱动、GE修正，既有攻击属性集不应出现鼠/牛/虎等硬编码字段。

## 十三、分步实施计划（任务化，可直接用于代码开发）

| 里程碑 | 工作内容 | 改动归属 | 必须通过的验收 |
| --- | --- | --- | --- |
| **M0 保全与基线** | 锁定5类属性集/24字段反射标识、复用现有伤害公式和ABI（接口二进制兼容），盘点提交前未保存的其他任务修改 | Tests/Architecture（架构测试）与现有Docs（文档） | 无重复字段、无隐式改值入口、无无关文件变更 |

| **M4 伤害/治疗计算** | 捕获式属性计算审查，保护当前物理/法术/真实伤害、暴击、穿透、盾吸收和重放幂等 | GamePlatformCombat（平台战斗） | 旧公式和服务器事件回放数值不回归 |
| **M5 再生与气势** | 打通AttackSpeed、PoiseRegen与MomentumGain/Decay真实消费；用权威GE或低频调度替代角色UI逐帧轮询 | GamePlatformCombat/DBAGameplay（战斗/玩法） | 1v1到5v5、NPC密集场景下不累积重复定时器 |
| **M6 Buff与UI事件** | GE层状态授权、多来源实例ID、图标排序、危急控制、断线恢复；使用现有UI蓝图与ViewModel | GamePlatformUI/DBAClient（平台UI/客户端） | Buff/Debuff与GAS同步，换目标/地图不显示旧数据 |
| **M7 网络与发布门禁** | Automation（原生自动化）、PIE（编辑器运行）、Dedicated Server双客户端、Cook（资源烘焙）与性能回归 | 各模块自身测试/构建 | 客户端、服务器不误加载Editor/UI私有资源；权限隔离、数值一致 |

**推荐执行顺序：M0 → M1 → M3 → M2 → M4 → M5 → M6 → M7。** M1和M3先行是为了清除多人复制与属性上限不一致的风险；不要在这些门禁未通过时大面积创建能力和项目GE资产。

## 十四、最小必要测试矩阵

1. **反射/重复：** 五组属性集真实存在，全部字段唯一，当前24字段维持历史GAS名称与类型；一角色只使用一个ASC。
2. **数值：** NaN、Inf、负值、概率越界、MaxHealth/MaxShield/MaxPoise/MaxMomentum变化、Buff结束后的Base与Current恢复。
3. **公式：** 物理/法术/真实伤害、护盾吸收、暴击、治疗上限、Tenacity完全免控、Poise扣减/恢复。
4. **效果：** 两名施放者产生同类型Buff、叠层刷新/移除/驱散、DoT/HoT周期执行、免疫状态回退。
5. **生命周期：** 角色首次出生、换Hero、Possess、玩家重连、客户端延迟复制、世界切换、重生后旧角色事件不会复活。
6. **安全：** 没有客户端数值写入路径；迷雾敌人属性和GE来源不泄漏；服务器事件重复提交不会重复生效。
7. **性能：** 5v5与多NPC的ASC内存、复制字节量、属性委托数、GE周期调度与GameThread（游戏线程）成本有可复核基线。
8. **发布：** Win64 Editor/Client/Server模块均能构建、真正Cook、双客户端+专服自动验收。测试源码编译≠已执行。
