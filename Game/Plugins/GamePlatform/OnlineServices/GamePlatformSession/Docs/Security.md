# D06｜安全边界与未解决威胁

Gateway认证、TransferTicket、默认UE Transport、服务器Admission Provider和拥有者RPC握手已经实现，但完整Session网络链仍不应仅凭源码存在按生产完成状态发布。当前剩余重点是UE构建、双进程E2E、断线/重连、Boot切换和日志泄漏实测。

控制面边界是Online/服务器到业务后端的受保护连接。Online独占访问与刷新令牌；Session不读取Token。Gateway `world-entry` 使用Bearer认证当前玩家并核对已选角色；GameServerControl内部HTTP统一使用内部Bearer，服务器作用域操作同时核对 `X-Game-Server-Id` 与 `X-Game-Server-Boot-Id`，Backend再与当前注册实例Boot比较。这些门禁不替代HTTPS/私网和服务身份体系；生产部署仍必须保证每个进程BootId唯一且内部Bearer安全注入。

游戏网络边界是UE客户端到Dedicated Server。默认Transport使用不带Query/Fragment的绝对ClientTravel；一次性TransferTicket不进入Travel URL。目标服务器在真实PostLogin PlayerController上动态挂载只复制给拥有者的Admission握手组件，客户端通过Reliable Server RPC提交票据，服务器通过当前Controller生成ConnectionId/ConnectionGeneration并调用唯一Admission Provider。OperationId/AttemptId只承担幂等/关联作用，真正授权依赖服务端对签名Ticket、目标实例Boot和协议版本的校验。

当前ServerTransfer票据使用HMAC-SHA256签名、随机Nonce、短TTL、目标GameServer/Boot/Protocol/Assignment/World/Experience绑定，并由ReplayStore一次性消费。签名密钥要求至少32字节，生产从部署Secret注入；当前协议尚未实现多key轮换的keyId/issuer/audience模型，因此密钥轮换和跨集群发行策略仍需部署层补充。Credential原文只在客户端Transport、拥有者RPC与单次Admission HTTP请求生命周期内短暂存在，并主动清零字节缓冲，不写日志。

防重放采用两层：TicketID由ReplayStore原子SET-NX消费；SessionEpoch由共享EpochStore在签票时递增，并在验票时原子维护 `(SessionID, 已接受Epoch, TicketID)` 栅栏。同Epoch同Ticket允许基础设施故障后的幂等重试，低Epoch或同Epoch不同Ticket在Replay消费前拒绝。这样更高代次一旦准入，未使用的旧票也不能重新建立权威连接。真实双连接竞态仍需E2E压测证明。

双活防护当前首先依赖目标绑定的单调SessionEpoch、客户端HighestAcceptedSessionEpoch、服务器已接受Epoch栅栏和ServerBootId。它能阻止旧票/旧Boot重新准入，但尚未实现持续在线会话租约、来源服主动踢出确认和跨服期间完整的权威Gameplay冻结，因此仍不能把“准入防旧”扩大解释为“所有Gameplay双活问题已解决”。

测试库采用独占容器、network=none；Go测试进程加入该容器网络命名空间，通过127.0.0.1访问PostgreSQL，没有发布宿主端口。此测试显式使用trust及sslmode=disable，仅适用于该封闭测试拓扑，不是控制面TLS验收，更不允许据此扩展私网/公网豁免。

Session快照只含非敏感Binding身份，TransferTicket只在请求/Transport/握手边界短期传递；Endpoint校验拒绝查询参数、换行和URL式凭据拼接，默认Transport明确只把纯Endpoint传给ClientTravel。代码路径已经避免主动日志记录Ticket，但仍必须在真实E2E后扫描引擎Browse/NetworkFailure/Crash日志、命令行、快照和产物，确认第三方/引擎层没有间接泄漏。正式服务角色最小授权、TLS、证书与密钥轮换仍需部署审查。
