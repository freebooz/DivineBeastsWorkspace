# GamePlatformSettings 审查整改方案与执行计划

日期：2026-09-29

## 一、审查结论

审查前插件只有 `GamePlatformSettingsClient` 模块入口，缺少公开契约、设置模型、注册表、解析、快照、版本迁移、端侧配置、测试和可追溯文档，属于正式基线中的空壳。

本轮结合现行工程与专项实现任务重新判定：**GamePlatformSettings 应保留并建设为平台层统一设置基础设施，不应退休。**

原因：

- 设置描述、注册、分层解析、快照、版本迁移是跨项目稳定能力。
- 客户端 `UGameUserSettings` 和服务器部署配置需要不同端侧适配，但可共享类型安全 Registry/Resolver。
- MobaCommon 与 DivineBeasts 需要通过 Provider 扩展，而不是修改平台代码。
- Editor/CI 必须在发布前发现 Provider/SettingId/作用域冲突。

当前工程层名仍使用 `GamePlatform（游戏平台基础层）`，不新增第二套 GameFoundation 目录。

## 二、主要原有问题与严重程度

### P0：空壳占位
只有模块注册，没有真实服务和消费者契约。

### P0：职责边界模糊
旧文档把 Graphics／Audio／Input／Camera／Accessibility 混在 Settings 规划里，存在吞并领域插件的风险。

### P0：没有通用 Provider / Registry / Resolution
上层无法无反向依赖地注册项目／MOBA设置，也没有重复 ID、类型、端侧冲突检测。

### P0：Client / Server 配置体系缺失
服务器没有 INI／Environment／CommandLine 确定性覆盖；客户端没有 User 层版本化持久化。

### P1：没有 Snapshot / 批量事件
调用方只能潜在直接访问底层配置，容易重复解析和事件风暴。

### P1：没有迁移与损坏恢复
版本升级存在删除旧配置或半迁移风险。

### P1：图形设置可能重复造轮子
必须复用 UE5.8 UGameUserSettings，而不是再建一套显示／Scalability 系统。

### P1：性能和生命周期未定义
缺少 0 Tick、低频 Apply、显式 Save、异步 IO、GameInstance 作用域和多 PIE 隔离约束。

### P1：异步 Save 与 Provider 拓扑变化存在代次竞态
原实现的 Modular Feature 注册／注销事件会直接 `ReloadInternal()`，即使 User Save 正在异步执行。整改为 Save 期间只记录 PendingTopologyReload；只有保存成功且保存代次仍等于当前 MutationGeneration 时才处理重载，失败或期间有新修改则继续延后。

### P1：敏感标记存在错误安全预期
`bSensitive` 原本只做日志脱敏，但 SaveGame／INI／环境变量／命令行不是秘密存储。整改为敏感 Descriptor 只允许 Session 临时作用域；Server 对敏感持久化覆盖 Fail Closed；凭据、令牌和密钥继续使用部署秘密机制。

### P1：String 设置无容量边界
通用 String 原本可接收无界文本。整改为统一 4096 字符安全上限，文本解析和 Descriptor 值验证双重拒绝超长输入。

### P1：Server敏感Descriptor误阻断
原Server Provider只要遇到 `bSensitive` Descriptor 就直接加载失败，即使没有任何外部覆盖。整改为允许敏感Session Descriptor存在，仅当INI／Environment／CommandLine真实尝试注入时Fail Closed。

### P1：端侧默认层可能串用
原Descriptor默认 `PersistenceScope=User + RuntimeScope=Any`，且ServerDefault没有强制Server端侧，存在客户端错误消费服务器默认语义的风险。整改为安全默认 `Project + Any`，User必须Client、Server必须Server，ServerDefault必须Server+ServerScope。

### P1：Server环境变量键规范化冲突
不同SettingId在转换为 `GP_SETTING_*` 时可能得到同名环境变量。整改为服务器加载前检测规范化键冲突并Fail Closed，不依赖TMap或Provider遍历顺序。

### P0：User Profile 缺少账号隔离
原 Client Persistence 固定写入同一个 SaveGame 槽和 `UserIndex=0`，未来一旦接入 User 层生产Provider，同设备切换账号会共享偏好。整改为基础层新增不依赖Online的 `SwitchUserContext` 中立契约，上层只注入不透明稳定键；Client以SHA-1派生槽隔离账号，Logout空键不读写User Profile，存在脏数据／待Apply／异步Save时拒绝切换。

### P1：当前没有生产 Provider
四模块代码已经存在，但全工程只有自动化测试 Provider，没有非测试 `IGamePlatformSettingsProvider`。因此 Runtime／Server／Editor 现阶段只能判定“框架实装”，禁止把现有 Input／UI／Camera／SFX 设置复制到 User 层形成双重真源。

## 三、最终修改方案

1. 建立 `GamePlatformSettingsRuntime`：Descriptor、Provider、Registry、Validation、Resolution、Snapshot、ChangeSet、Migration、Diagnostics、统一 Service。
2. 建立 `GamePlatformSettingsClient`：UGameUserSettings 设备设置事务 + User Profile 异步持久化。
3. 建立 `GamePlatformSettingsServer`：ServerDefault／Deployment／Environment／CommandLine 只读覆盖。
4. 建立 `GamePlatformSettingsEditor`：Provider/Descriptor 静态校验。
5. 四模块只通过 Runtime 公共契约连接，不直接依赖 Input/UI/Camera/SFX/Online/Session/项目层。
6. Runtime 使用 GameInstance 生命周期、0 Tick、TMap Registry/Snapshot。
7. User 设置按内存 Dirty → Apply → 显式异步 Save；设备显示按 Stage→Preview→Confirm/Cancel。
8. Migration 使用逐版本唯一链且副本提交。
9. Dedicated Server 排除 Client/Editor 模块和表现依赖。
10. 文档同步 Architecture/API/Lifecycle/Extension/Migration/Performance/Testing/ManualReview/组件清单。

## 五、回退与兼容

本轮未修改 Shared 跨语言协议、资产身份、后端 API 或数据库。新增 API 原先不存在，因此没有旧公开调用方破坏风险。

回退应以插件内新增四模块实现和描述装配为单位，不删除其他插件代码；不得通过注释错误代码、空实现或移除测试来伪造构建成功。
